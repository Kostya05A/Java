## Импорт — операция, которая должна быть атомарной

Импорт читает файл и наполняет каталог. Если он упал на третьей строке
из десяти, в каталоге окажется либо ничего, либо первые две записи.
Второй вариант хуже первого: каталог наполовину новый, наполовину
старый, и **непонятно, какое состояние считать верным**. Повторный
запуск импорта поверх такого состояния даёт третий вариант.

Поэтому контракт жёсткий: **либо применяются все записи, либо ни одна**.

```java
public int importFrom(Path file) throws SourceUnavailableException, ImportAbortedException {
    List<String> lines = readLines(file);

    Map<CourseCode, Course> stateBefore = catalog.snapshot();   // снимок ДО изменений

    int recordNumber = 0;
    try {
        for (String line : lines) {
            recordNumber++;
            if (line.isBlank()) continue;
            catalog.add(parseCourse(recordNumber, line));
        }
    } catch (ImportAbortedException ex) {
        catalog.restore(stateBefore);                            // откат
        throw ex;
    }
    return recordNumber;
}
```

Это «транзакция без базы данных». Настоящее решение той же задачи —
`@Transactional` или `BEGIN/COMMIT/ROLLBACK`; здесь же важно само
решение: **откатное состояние снимается до первой записи, а не после
ошибки**, потому что после ошибки откатывать уже нечего было бы искать.

## Два отказа, а не один

| | `SourceUnavailableException` | `ImportAbortedException` |
|---|---|---|
| причина | файла нет, нет прав, битая кодировка | запись не соответствует формату |
| данные целы? | да | да, но в негодном виде |
| что делать | сообщить, повторить позже | прервать, откатить, попросить починить файл |
| откат | не нужен — не начато ни одного изменения | обязателен |
| checked? | да | да |

Почему нельзя объединить в один тип: вызывающий обязан вести себя
по-разному. При недоступном файле оператору нужно «дай доступ и
повтори», при плохой записи — «вот номер строки, почини». Один тип
означал бы, что из текста сообщения надо угадывать, что случилось,
а это ровно то, ради чего задание 6 учило сохранять `cause`.

### Кодировка — отдельный случай

```java
} catch (MalformedInputException ex) {
    throw new SourceUnavailableException(file,
            "Файл не в кодировке UTF-8", ErrorCode.MALFORMED_RECORD, ex);
} catch (IOException ex) {
    throw new SourceUnavailableException(file,
            "Файл импорта недоступен", ErrorCode.SOURCE_UNAVAILABLE, ex);
}
```

Два отказа одного типа, но с **разными кодами**: файл существует
и не читается как текст — это проблема данных, а не доступа.
Оператору нужны разные действия. Ловится `MalformedInputException`
раньше `IOException`, потому что он идёт первым в цепочке наследования.

## Отказ записи: всё, что может отвергнуть, сводится к одному типу

```java
private Course parseCourse(int recordNumber, String rawRecord) throws ImportAbortedException {
    String[] parts = rawRecord.split(";");
    if (parts.length != 3) {
        throw new ImportAbortedException(recordNumber, rawRecord,
                "ожидалось 3 поля, получено " + parts.length);
    }
    ...
}
```

Три принципа, которые здесь видны лучше, чем в задании 6:

1. **Мягкая проверка вместо исключения там, где отказ штатный.**
   `CourseCode.isValid(rawCode)` возвращает `false`, а не бросает:
   невалидный код в строке файла — это отказ записи, а не падение.
   Проверка через `isValid` читается как «если код не годен — отказ»,
   а `try { of() } catch` выглядел бы так, будто мы боимся своего кода.
2. **Ловится только то, что можно перевести.** Только
   `NumberFormatException`; `NullPointerException` пролетел бы насквозь.
3. **`cause` сохраняется.** Тест `numberFormatCausePreserved` требует,
   чтобы исходный `NumberFormatException` был в `getCause()`: по нему
   видно, что именно не так с текстом «сорок» — пустая строка,
   переполнение или мусор.

## Что в исключении, а что нет

```java
public ImportAbortedException(int recordNumber, String rawRecord, String message, Throwable cause)
```

| Поле | Зачем |
|---|---|
| `recordNumber` | оператор сразу находит строку |
| `rawRecord` | номер строки в логе может не совпасть с файлом после правок |
| `message` | что именно не так, без сырых данных |
| `cause` | низкоуровневая причина для инженера |

В `toString()` нет ни пути к файлу, ни содержимого записи — это
детали для лога, а не для пользователя (ср. задание 15).

## Снимок состояния: почему `snapshot`, а не «очистить и загрузить заново»

Откат делается через два метода хранилища курсов:

```java
public Map<CourseCode, Course> snapshot() {
    return Map.copyOf(courses);
}

public void restore(Map<CourseCode, Course> state) {
    courses.clear();
    courses.putAll(state);
}
```

`Map.copyOf` отдаёт **копию**, а не ссылку на живой словарь. Это принципиально:
е бы `snapshot()` возвращал сам `courses`, то `restore(state)` после частичного
импорта очистил бы и сам снимок тоже — откатывать было бы нечего.

Каталог при этом хранит не копии курсов, а ссылки на те же объекты. Это
допустимо: импорт только добавляет и заменяет записи целиком, а не меняет
внутреннее состояние уже загруженного курса. Если бы курс мог измениться
после импорта, понадобился бы глубокий снимок.

Ошибка «откат к пустому каталогу» вместо снимка — самая частая здесь:

```java
// ТАК НЕЛЬЗЯ: каталог формально пуст, но старые курсы потеряны
catch (ImportAbortedException ex) {
    catalog.restore(Map.of());
    throw ex;
}
```

Именно этот случай проверяет тест `rollbackRestoresPreviousContent`.

## Тесты: главный из них — про откат

```java
@Test
@DisplayName("откат: курсы из предыдущих строк не остаются в каталоге")
void rollbackKeepsCatalogUnchanged() {
    Path file = dir.resolve("bad.csv");
    Files.writeString(file, """
            JAVA-101;Основы Java;40
            WEB-200;Веб-разработка;30
            NOPE;Мусор;20
            """);

    ImportAbortedException ex = assertThrows(ImportAbortedException.class,
            () -> importer.importFrom(file));

    assertAll(
            () -> assertEquals(3, ex.recordNumber()),
            () -> assertEquals(0, catalog.size(), "ОТКАТ: ни одна запись не применена")
    );
}
```

Именно этот тест отличает «исключение бросили» от «откат сделали».
Без него удаление `catalog.restore(stateBefore)` из кода не сломало бы
ничего: тест на `assertThrows` остался бы зелёным, и поломка обнаружилась
бы только на рабочих данных.

Второй важный тест — **откат не затирает то, что было до импорта**:

```java
catalog.add(Course.of("OLD-001", "Старый курс", 10));
// ... неудачный импорт ...
assertEquals(1, catalog.size());
assertNotNull(catalog.find(CourseCode.of("OLD-001")));   // прежнее содержимое на месте
```

Откат к «пустому каталогу» вместо снимка — типичная ошибка: каталог
формально пуст, старые курсы потеряны, и никто об этом не узнал.

## Параметризованный список плохих записей

```java
@ParameterizedTest
@ValueSource(strings = {
        "JAVA-101;Основы Java",            // 2 поля вместо 3
        "JAVA-101;Основы Java;40;лишнее", // 4 поля
        "NOPE;Мусор;20",                   // неверный код
        "JAVA-102;;20",                    // пустое название
        "JAVA-103;Курс;сорок",             // часы не число
        "JAVA-104;Курс;5",                 // часы меньше минимума
        "JAVA-105;Курс;999"                // часы больше максимума
})
void everyMalformedFormRejected(String record) { ... }
```

Так проверяется не «один плохой случай», а **форма плохой записи**.
Когда появится восьмая форма (например, курс без часов), её будет куда
вписать, и она не пройдёт молча.

## Практическая заметка: `@TempDir` и параметры

```java
// НЕ РАБОТАЕТ: JUnit не может решить, откуда взять Path
void everyMalformedFormRejected(@TempDir Path dir, String record) { }
```

Сообщение об ошибке: `Discovered multiple competing ParameterResolvers
for parameter [java.nio.file.Path arg0]` — `@TempDir` и параметр
параметризованного теста претендуют на одну и ту же `Path`. Решение —
своя директория в `@BeforeEach` плюс удаление в `@AfterEach`:

```java
@BeforeEach
void setUp() throws IOException {
    workDir = Files.createTempDirectory("course-import-test");
}

@AfterEach
void tearDown() throws IOException {
    try (var paths = Files.walk(workDir)) {
        paths.sorted(Comparator.reverseOrder()).forEach(...delete...);
    }
}
```

## Сводка

| Решение | Причина |
|---|---|
| Снимок состояния до первой записи | Откатывать надо то, что было до импорта |
| `restore` в `catch`, а не в `finally` | Откат нужен только при отказе, не при успехе |
| Два типа отказа вместо одного | Разная реакция вызывающего |
| `MalformedInputException` отдельно | «Файл не в UTF-8» — проблема данных, а не доступа |
| `isValid` вместо `try/catch` | Невалидный код — отказ, а не падение |
| `cause` сохраняется | Низкоуровневая причина нужна инженеру |
| Параметризованный список плохих записей | Проверяются формы, а не один случай |
