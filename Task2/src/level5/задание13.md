# Задание 13. Таблица решений сервиса зачисления

Код: `src/domain/EnrollmentService.java`, тесты: `test/level5/EnrollmentDecisionTableTest.java`

```bash
./mvnw test -Dtest=EnrollmentDecisionTableTest
```

## Зачем нужна таблица, а не цепочка if-ов

`enroll` решает одну задачу: по набору условий выбрать исход. Условий
несколько, и порядок их проверки влияет на результат — при двух
одновременных нарушениях код отказа зависит от того, что проверили первым.
Список «если … то …» быстро перестаёт читаться:

```java
if (course == null) return reject(COURSE_NOT_FOUND);
if (closed) return reject(COURSE_CLOSED);
if (enrolled) return reject(DUPLICATE);
if (!prereqOk) return reject(PREREQ_MISSING);
if (noSeats) { waitlist(); return waitlisted(); }
return accepted();
```

Тот же код в виде таблицы — это одновременно спецификация и основа
для параметризованного теста. Каждая строка обязана быть реализована
и обязана быть проверена.

## Порядок проверок не случаен

Строки таблицы проверяются сверху вниз, и порядок отражает
«фундаментальность» отказа:

1. **Курс существует.** Если курса нет, дальше смотреть не на что:
   ни статус, ни места не имеют значения.
2. **Курс открыт.** Закрытый курс отвергает любого, у кого выполнены
   все прочие условия. Проверка статуса раньше остальных даёт один
   и тот же ответ на все вопросы вида «а почему не зачислили?».
3. **Нет повторной заявки.** Проверка дубликата раньше листа ожидания:
   иначе повторные отправки формы от одного человека раздували бы
   лист ожидания десятками одинаковых записей.
4. **Пререквизиты.** Непройденный пререквизит — содержательный отказ
   («вы не готовы»), а не «мест пока нет». Ставить человека в лист
   ожидания из-за пререквизита бессмысленно: место освободится, а он
   всё равно не сможет начать.
5. **Места.** Последним, потому что это единственное условие,
   исход при котором — не отказ, а лист ожидания.

Порядок проверяется тестами `closedCourseWinsOverEverythingElse`
(строка 2 при выполненных 3–5) и `duplicateBeatsWaitlist`
(строка 3 при отсутствии мест).

### Одна тонкость: «уже заявлен» — это и зачислен, и в листе

```java
if (course.isEnrolled(studentId) || course.isWaitlisted(studentId)) {
    return EnrollmentResult.rejected(studentId, courseCode, ErrorCode.DUPLICATE_APPLICATION);
}
```

Только `isEnrolled` было бы недостаточно: студент, попавший в лист
ожидания, при повторной отправке формы получил бы `WAITLISTED` снова
и снова. Тест `duplicateBeatsWaitlist` фиксирует, что лист не
раздувается.

## Тест как таблица

Параметризованный тест повторяет строки таблицы один в один:

```java
@ParameterizedTest(name = "[{index}] есть={0} открыт={1} дубликат={2} пререквизит={3} места={4} -> {5} {6}")
@MethodSource("decisionTable")
void decisionTableIsExhaustive(boolean courseExists, boolean open, boolean duplicate,
                               boolean prerequisitesMet, boolean hasFreeSeat,
                               EnrollmentResult.Status expectedStatus, ErrorCode expectedReason) { ... }
```

Тонкость, на которой такие тесты обычно и ломаются: **подготовка должна
точно соответствовать заявленному набору условий**. Первый вариант теста
всегда создавал транскрипт с пройденным пререквизитом — и строка
«пререквизит не пройден» проверяла не своё. Лечение:

```java
service = new EnrollmentService(catalog,
        prerequisitesMet ? transcriptsOf("JAVA-101") : transcriptsOf());
```

и для «мест нет» — не выдумывать состояние, а занять единственное место
другим студентом:

```java
Course course = new Course(WEB, "Веб", 1);
if (duplicate) {
    course.enroll(STUDENT);      // уже зачислен
} else if (!hasFreeSeat) {
    course.enroll(999L);         // место занято другим
}
```

Значения ожиданий живут в `@MethodSource("decisionTable")` — в одном
месте рядом друг с другом, и по нему видно, что таблица полна.

## Ошибка как значение

```java
public EnrollmentResult enroll(long studentId, CourseCode courseCode) { ... }
```

Метод **не бросает** исключений для доменных отказов: их четыре, они
перечислены в `ErrorCode`, и каждый встречается в обычной работе.
Исключение здесь означало бы, что «курс закрыт» — exceptional path,
а вызывающий обязан писать `try/catch` ради ветки, которая сегодня
срабатывает у каждого пятого.

Исключение оставлено в отдельном методе для случая, когда отказ
недопустим:

```java
public EnrollmentResult enrollOrFail(long studentId, CourseCode courseCode) {
    EnrollmentResult result = enroll(studentId, courseCode);
    return switch (result.status()) {
        case ACCEPTED, WAITLISTED -> result;
        case REJECTED -> throw new EnrollmentRejectedException(
                studentId, courseIdOf(courseCode), reasonOf(result.reason()));
    };
}
```

Тот же домен, другое требование вызывающего: «мне нужен успех или
исключение, промежуточного исхода быть не должно».

## Обратная операция: `removeStudent`

Зачисление разбирает исход, потому что там исходов несколько. Отчисление
устроено иначе:

```java
public boolean removeStudent(long studentId) {
    waitlist.remove(studentId);
    return enrolledStudentIds.remove(studentId);
}
```

Метод убирает студента и из списка зачисленных, и из листа ожидания, и
возвращает `true`, только если он был зачислен. Исключения здесь нет, и
это осознанно: отчисление несуществующего студента — не ошибка, а
повторный вызов, который ничего не меняет. Вызывающий всё равно не смог бы
ничего исправить, поэтому бросать исключение было бы несоразмерно.

Разница с зачислением видна прямо в контракте:

| | `enroll` | `removeStudent` |
|---|---|---|
| Возможных исходов | 5+ (см. таблицу) | 1 успешный, независимо от входа |
| Отказ | значение с причиной | не отказ, а ничего не изменилось |
| Исключение | `enrollOrFail` — отдельный метод | не бывает |

## Про `switch` без `default`

В `reasonOf` нет ветки `default`, и это сделано намеренно:

```java
return switch (code) {
    case PREREQ_MISSING -> Reason.PREREQ_MISSING;
    ...
    case MALFORMED_RECORD, SOURCE_UNAVAILABLE, OK ->
            throw new IllegalArgumentException("нет доменной причины для кода " + code);
};
```

Если в `ErrorCode` появится новое значение, компилятор перестанет
компилировать файл, пока ветка не будет написана. С `default`-веткой
код собрался бы и тихо вернул бы, например, `NO_SEATS` на код
`SOURCE_UNAVAILABLE` — отказ, которого не бывает, был бы выдан как отказ,
который бывает.

Именно так в проект попалось `Reason.COURSE_NOT_FOUND`: таблица вернула
`REJECTED` с этим кодом, `reasonOf` не знал такой причины и бросал
`IllegalArgumentException` — штатный отказ выглядел как баг.
Полнота `switch` — это не формальность, а проверка согласованности
между двумя перечислениями.
