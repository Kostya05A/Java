# Задание 12. Устранить хрупкие тесты

Код: `test/level4/FragileTestsFixedTest.java`

```bash
./mvnw test -Dtest=FragileTestsFixedTest
```

В `pom.xml` у surefire уже включено `<runOrder>random</runOrder>` —
каждый прогон даёт случайный порядок выполнения. Это не украшение:
случайный порядок — дешёвый способ найти тесты, которые зависят от соседей.

## Что такое хрупкий тест

Хрупкий (flaky) тест проходит в одном прогоне и падает в следующем,
причём код между прогонами не менялся. Причина всегда одна из трёх:

* тест зависит от порядка выполнения;
* тест делит изменяемое состояние с другими тестами;
* тест зависит от внешнего окружения (текущая директория, время, сеть).

Отдельно стоит выделить четвёртую проблему — **тест, который ломается
от безобидного изменения**: сверка полного текста `toString`. Формально
он не flaky, но ведёт себя так же: переставил fields в `toString` для
удобства вывода — тест красный, поведение объекта не изменилось.

## 1. Зависимость от порядка выполнения

```java
// БЫЛО
@Test
void courseIsCompleted() {
    assertTrue(course.isCompleted());      // а где completeHours()?
    assertEquals(20, course.completedHours());
}
```

Тест не падает только потому, что выше по файлу (или в другом файле
раньше по алфавиту) отработал `completeHoursTest()`. Это опаснее
обычной ошибки: при любом переименовании, удалении или
`@Disabled` соседнего теста этот тест начнёт падать, и падение будет
выглядеть загадочно — код-то не менялся.

**Лечение — Arrange внутри теста.** Тест должен быть самодостаточным:

```java
// СТАЛО
@Test
void isSelfContained() {
    sharedCourse.completeHours(20);       // Arrange здесь же

    assertAll(
            () -> assertTrue(sharedCourse.isCompleted()),
            () -> assertEquals(20, sharedCourse.completedHours())
    );
}
```

`@BeforeEach` с пересозданием объекта — тоже лечение, но хуже
подхода «Arrange в теле теста»: он прячет состояние, из-за которого
тест зависит от порядка, в место, куда надо специально заглядывать.
Практика: дешёвые объекты создавать в теле теста, тяжёлые фикстуры
инициализировать в `@BeforeEach`.

Хрупкий вариант оставлен в тесте как `@Disabled` — держать его
включённым нельзя, он сделал бы прогон нестабильным.

## 2. `static`-состояние

```java
private static final AtomicInteger GLOBAL_COUNTER = new AtomicInteger();

@Test
void wasBrokenByStaticState() {
    assertEquals(0, GLOBAL_COUNTER.get());   // верно, только если тест первый
    GLOBAL_COUNTER.incrementAndGet();
}
```

`static` переживает и тест, и метод, и весь прогон. Проверка «ожидаю ноль»
верна ровно до первого обращения к счётчику из любого места.

Опасный вариант, который встречается в реальных проектах, — `static` не
счётчик, а кэш или реестр:

```java
static final Map<String, Course> CACHE = new HashMap<>();
```

Здесь тест может «проходить» из-за того, что другой тест положил в кэш
нужный объект, и падать в CI, где порядок другой или тесты идут
параллельно.

**Лечение — состояние на уровне теста или экземпляра:**

```java
@Test
void isIndependentOfOtherTests() {
    AtomicInteger localCounter = new AtomicInteger();
    localCounter.incrementAndGet();
    localCounter.incrementAndGet();

    assertEquals(2, localCounter.get());
}
```

Если состояние действительно нужно общим (сценарий «две части одного
сценария»), его создают явно внутри одного теста, а не прячут в `static`.

## 3. Зависимость от текущей директории

```java
// БЫЛО
Path file = Path.of("testdata", "courses.csv");   // относительный путь
String content = Files.readString(file);
```

`Path.of("a", "b")` без ведущего `/` разрешается относительно
`user.dir` — директории, из которой запущен процесс. Запуск из корня
проекта работает; запуск из `target/`, из IDE с другим working directory
или в CI даёт `NoSuchFileException`. Тест при этом «работает у меня».

Два устойчивых варианта:

**`@TempDir`** — JUnit создаёт временную директорию и удаляет её после теста:

```java
@Test
void isIndependentOfWorkingDirectory(@TempDir Path tempDir) throws IOException {
    Path file = tempDir.resolve("nested").resolve("courses.csv");
    Files.createDirectories(file.getParent());     // проверим и создание каталогов
    Files.writeString(file, "JAVA-101;Основы Java;40", UTF_8);

    assertEquals("JAVA-101;Основы Java;40", Files.readString(file));
}
```

**Ресурс в classpath** — для фикстур, которые должны быть одинаковыми
на всех машинах. В этом проекте `pom.xml` переопределяет
`testResources` на `src/test/resources`, поэтому фикстура
`src/test/resources/testdata/courses.csv` доступна так:

```java
try (var stream = FragileTestsFixedTest.class
        .getResourceAsStream("/testdata/courses.csv")) {
    assertNotNull(stream, "фикстура должна быть в classpath");
    String content = new String(stream.readAllBytes(), UTF_8);
    assertTrue(content.contains("JAVA-101"));
}
```

Разница принципиальная: `@TempDir` — про временные файлы,
которые тест создаёт сам; classpath — про статичные данные,
которые нужны неизменными. Смешивать их не стоит: тест, который
создаёт свой файл в `testdata` и тут же его читает по относительному
пути, хрупок по второй причине, а не по первой.

Ещё одно правило: **отсутствие фикстуры не должно валить тест на
`FileNotFoundException`** — но и молчать нельзя. Компромисс — явная
проверка, что ресурс доступен, с понятным сообщением (как в примере выше),
а не `catch (IOException ignored)`.

## 4. Сверка полного текста `toString`

```java
// БЫЛО
assertEquals("Course[JAVA-101 'Основы Java', status=OPEN, capacity=30, "
             + "enrolled=0, completedHours=20]", course.toString());
```

Тест фиксирует не контракт, а форматирование. Изменения, которые его
сломают, не имеют отношения к поведению:

* добавили поле `ownerId` в `Course` и в `toString`;
* поменяли порядок полей;
* перевели вывод на `String.format` с другими отступами;
* добавили перенос строки в длинных значениях.

**Лечение — проверять наблюдаемые свойства, а не их склейку:**

```java
@Test
void checksPropertiesNotString() {
    Course course = Course.of("JAVA-101", "Основы Java", 30);
    course.completeHours(20);

    assertAll(
            () -> assertEquals(CourseCode.of("JAVA-101"), course.code()),
            () -> assertEquals("Основы Java", course.title()),
            () -> assertEquals(30, course.capacity()),
            () -> assertEquals(20, course.completedHours()),
            () -> assertEquals(CourseStatus.OPEN, course.status())
    );
}
```

Проверки здесь лучше, чем в `CourseFailureStateTest`: они **упали бы
при любом изменении поведения**, а не при любом изменении текста.
Разница в том, что первая проверка бесполезна, а вторая ловит баг.

Сюда же относится enum `CourseStatus` вместо boolean `closed`: в логе и в
сообщении об ошибке `status=CLOSED` читается сразу, а `closed=true` пришлось
бы расшифровывать. Значение при этом не изменилось — поменялось только то,
как оно названо, и потому хрупкий тест на текст упал бы первым.

Если `toString` проверять всё-таки нужно (например, это формат лог-строки
и его читает парсер), проверяют **фрагменты**, на которые опирается
диагностика:

```java
assertAll(
        () -> assertTrue(text.contains("JAVA-101")),
        () -> assertTrue(text.contains("Основы Java"))
);
```

Тогда появление нового поля в `toString` тест не тронет, а потеря
идентификатора курса — поймает.

## 5. Проверка, что зависимости от порядка нет

Способы отловить хрупкость до того, как она поймает вас на CI:

| Способ | Команда / действие |
|---|---|
| Случайный порядок | уже включено: `<runOrder>random</runOrder>` в `pom.xml` |
| Прогон только одного метода | `./mvnw test -Dtest='FragileTestsFixedTest#isSelfContained'` |
| Параллельный прогон | `./mvnw test -Dparallel=classes -DthreadCount=4` (нужен `junit-platform.properties`) |
| Чистая проверка | тест, сравнивающий два независимых прогона: `pureFunctionHasNoMemory` |

Отдельно полезный тест-индикатор: если объект не хранит состояние между
вызовами, два одинаково построенных экземпляра дают одинаковые значения.
`pureFunctionHasNoMemory` проверяет именно это — и упадёт, если где-то
появится скрытое состояние.

## Сводка

| Хрупкость | Лечение |
|---|---|
| Зависимость от порядка | Arrange внутри теста; `@BeforeEach` для тяжёлых фикстур |
| `static`-состояние | Локальная переменная или поле экземпляра |
| Относительные пути | `@TempDir` или ресурс из classpath |
| Сверка всего `toString` | Проверка свойств; для логов — `contains` по фрагментам |
| «У меня работает» | Случайный порядок, одиночный запуск метода, параллельный прогон |
