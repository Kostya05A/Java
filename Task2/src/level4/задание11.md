# Задание 11. `assertThrows` и состояние после отказа

Код: `test/level4/CourseFailureStateTest.java`

```bash
./mvnw test -Dtest=CourseFailureStateTest
```

## 1. Проверяем не только тип

`assertThrows` возвращает пойманное исключение, поэтому проверять можно
не только класс, но и содержимое:

```java
IllegalArgumentException ex = assertThrows(
        IllegalArgumentException.class,
        () -> course.completeHours(100));

assertAll(
        () -> assertTrue(ex.getMessage().contains("100"),
                "сообщение должно называть отвергнутое значение"),
        () -> assertTrue(ex.getMessage().contains("40"),
                "сообщение должно называть границу")
);
```

Почему одного типа мало:

```java
assertThrows(IllegalArgumentException.class, () -> course.completeHours(100));
```

Этот тест зелёный и в случае, когда метод бросает `IllegalArgumentException`
с пустым сообщением, или с текстом `"null"`, или вообще ни о чём не
говорящим. Пользователь увидит «что-то пошло не так», инженер в логе увидит
то же самое. Контекст ошибки потерян — а ради него всё и затевалось
(сравните с `NumberFormatException` из задания 6).

Что именно проверять, зависит от типа:

* **своё исключение с полями** — проверять поля, а не текст:
  `assertEquals(studentId, ex.studentId())`, `assertEquals(reason, ex.reason())`.
  Это надёжнее `contains`: поля меняются вместе с логикой, текст — нет;
* **стандартное исключение** — проверять смысл сообщения через `contains`,
  а не точное равенство (текст переводят, деталь реализации меняется).

`assertAll` собирает все проверки и показывает сразу все несовпадения.
Обычная последовательность `assert` упала бы на первой и не показала бы
вторую проблему.

## 2. Состояние после неудачной команды

```java
// Arrange
course.completeHours(20);
int hoursBefore = course.completedHours();

// Act
assertThrows(IllegalArgumentException.class, () -> course.completeHours(100));

// Assert
assertAll(
        () -> assertEquals(hoursBefore, course.completedHours(), "..."),
        ...
);
```

Это отдельное измерение качества кода. Класс, который **бросает исключение,
но уже изменил состояние**, нарушает ожидание вызывающего: тот ловит
исключение, откатывает UI-операцию, а объект остался в промежуточном
состоянии. Откатывать придётся вручную, а про эту операцию никто не знает.

Поэтому в `Course.completeHours` проверки идут **до** присваивания:

```java
public void completeHours(int hours) {
    if (hours < MIN_DURATION_HOURS) { throw ...; }
    if (hours > MAX_DURATION_HOURS) { throw ...; }
    this.completedHours = hours;      // только после всех проверок
}
```

И тест это фиксирует: `rejectedUpdateDoesNotOverwritePreviousValue` проверяет,
что неудачная попытка сменить 30 на 41 не затирает уже записанные 30.
Если бы реализация присваивала до проверки (или присваивала частично),
тест бы упал.

Проверено также: отказ `enroll` в закрытый курс не зачисляет студента
и не расходует место; повторная заявка не создаёт «вторую» запись;
отказ из-за отсутствия мест не меняет счётчики.

## 3. Одна причина падения в lambda

### Антипример

```java
// ТАК ДЕЛАТЬ НЕЛЬЗЯ
assertThrows(IllegalArgumentException.class, () -> {
    Course temp = new Course(CourseCode.of("BAD CODE"), "X", 1);  // может бросить сам
    course.completeHours(100);
});
```

Проблема не в том, что это не скомпилируется (скомпилируется), а в том,
**что именно поймает `assertThrows`**. Внутри lambda две операции, которые
могут бросить:

* `CourseCode.of("BAD CODE")` бросит свой `IllegalArgumentException`;
* `course.completeHours(100)` бросит ожидаемый.

`assertThrows` поймает **первое**. Тест будет зелёным, но проверяет он
совсем не то, что задумано: границу длительности он не проверил ни разу.
Чтобы это заметить, надо знать, что `of()` вообще может бросить.

Хуже — наоборот:

```java
// ТОЖЕ НЕЛЬЗЯ
assertThrows(IllegalArgumentException.class, () -> {
    course.completeHours(100);
    course.completeHours(200);      // вторая строка недостижима, но при смене
});                                 // контракта начнёт "падать" не там
```

Одна из проверок может оказаться мёртвым кодом, и при изменении реализации
тест начнёт «падать» на неверной причине.

### Правильно: подготовка наружу, в lambda только Act

```java
@Test
void onlyActInsideLambda() {
    int invalidHours = 100;                              // подготовка здесь, не падает

    IllegalArgumentException ex = assertThrows(
            IllegalArgumentException.class,
            () -> course.completeHours(invalidHours));    // только Act

    assertTrue(ex.getMessage().contains("100"));          // проверки - после
}
```

В `lambda` живёт **одна** команда, которая и должна упасть. Всё, что может
упасть по другой причине, выносится до `assertThrows` — тогда падение
подготовки будет видно сразу и укажет именно на неё
(`riskySetupRunsBeforeAssertThrows`).

### Правильно: несколько проверок одного результата — `assertAll`

```java
IllegalArgumentException ex = assertThrows(
        IllegalArgumentException.class,
        () -> course.completeHours(5));

assertAll(
        "причина отказа должна быть полной",
        () -> assertTrue(ex.getMessage().contains("5")),
        () -> assertTrue(ex.getMessage().contains("10")),
        () -> assertTrue(ex.getMessage().contains("минимум"))
);
```

`assertAll` не выполняет действия над SUT — только проверки уже полученного
значения, поэтому «одна причина падения» не нарушается.

### Сводка

| Правило | Зачем |
|---|---|
| В `lambda` — только Act | `assertThrows` поймает именно то, что проверяем |
| Подготовка, которая может бросить, — до `assertThrows` | Падение подготовки не маскируется под ожидаемое |
| Проверки результата — после, в `assertAll` | Видно все проблемы сразу, а не только первую |
| Проверяйте поля, а не текст `toString` | Текст — деталь реализации |

## Про `@BeforeEach`

```java
@BeforeEach
void createFreshCourse() {
    course = Course.of("JAVA-101", "Основы Java", 2);
}
```

Каждый тест получает **свой** объект. Это не стиль, а требование: общий
изменяемый объект в поле теста — источник зависимости от порядка
(подробно в задании 12).
