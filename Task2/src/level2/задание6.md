# Задание 6. Граница перевода исключения

Код: `RawNumberParser.java` (низкий уровень), `CourseImportService.java` (граница),
`CourseImportException.java` (новое исключение), `Demo6.java` (демонстрация).

```bash
./mvnw -q compile
java -cp target/classes level2.Demo6
```

## Идея

Слой импорта читает файл и для каждой записи зовёт низкоуровневый парсер.
Парсер не знает ни про файлы, ни про номера строк, ни про бизнес-правила — он
просто превращает текст в число:

```java
public static int parseHours(String text) {
    String value = text.startsWith("hours=") ? text.substring("hours=".length()) : text;
    return Integer.parseInt(value.trim());   // бросит NumberFormatException
}
```

Исключение поднимается **само**, из `Integer.parseInt`. Парсер его не ловит и
не переводит — это не его уровень ответственности.

## Перевод на границе

```java
public int parseHours(int recordNumber, String rawRecord, String hoursText)
        throws CourseImportException {
    try {
        return RawNumberParser.parseHours(hoursText);
    } catch (NumberFormatException ex) {                 // 1. ловим ТОЛЬКО это
        throw new CourseImportException(                 // 2. добавляем контекст
                recordNumber,
                rawRecord,
                "Неверный формат часов в записи №" + recordNumber,
                ex                                        // 3. сохраняем cause
        );
    }
}
```

Что даёт каждая строка:

| Шаг | Зачем |
|---|---|
| `catch (NumberFormatException ex)` | точный тип, а не `Exception` — см. ниже |
| `new CourseImportException(...)` | своё исключение с полями домена |
| `recordNumber`, `rawRecord` | информации, которой у `NumberFormatException` не было |
| `ex` последним аргументом | исходная причина сохраняется |

## Сравнение «до / после»

Без перевода:

```
java.lang.NumberFormatException: For input string: "сорок"
        at java.base/java.lang.Integer.parseInt(Integer.java: ...)
        at RawNumberParser.parseHours(RawNumberParser.java: ...)
        at ...
```

По этому тексту нельзя понять: какая строка файла, какое поле, что делать.
Файл мог содержать 100 000 строк — искать «сорок» вручную.

После перевода:

```
[0] CourseImportException: Неверный формат часов в записи №3
[1] java.lang.NumberFormatException: For input string: "сорок"
```

Плюс доступны `ex.recordNumber() == 3` и `ex.rawRecord() == "JAVA-101;Основы Java;сорок"` —
оператор открывает файл, идёт на строку 3 и чинит.

## Почему нельзя ловить `Exception`

```java
// ТАК ДЕЛАТЬ НЕЛЬЗЯ
try {
    return RawNumberParser.parseHours(hoursText);
} catch (Exception ex) {           // <- ловим вообще всё
    throw new CourseImportException(recordNumber, rawRecord, "ошибка импорта", ex);
}
```

Проблема не в том, что код не скомпилируется, — он скомпилируется. Проблема в
последствиях:

1. **Теряется различие между видами ошибок.** Сбой сети, баг программиста
   (`NullPointerException`), ошибка конфигурации и «плохое число» схлопываются
   в одно и то же «ошибка импорта». Вызывающий не может принять решение:
   для битой строки — попросить человека починить файл, для `NullPointerException` —
   чинить код;
2. **Прячется баг от разработчика.** `NullPointerException` в `parseHours` —
   это ошибка в коде. Если обернуть её в `CourseImportException`, в логе будет
   «запись №7 повреждена», и человек пойдёт чинить файл, а не код. Баг
   доживёт до продакшена;
3. **Ловится то, что нельзя обработать.** `catch (Exception)` внутри метода,
   который умеет только разбирать число, — это «на всякий случай».
   Реакции на `OutOfMemoryError` у него нет, и он всё равно попытается
   обернуть и его;
4. **Ломается контракт.** Сигнатура `parseHours` объявит `throws
   CourseImportException`, и вызывающий будет обязан обработать импорт-ошибку
   там, где на самом деле может быть баг.

Правило: **ловить нужно ровно то, что умеешь превратить в осмысленный ответ.**

## Почему здесь `CourseImportException` — checked

`extends Exception`, не `RuntimeException`:

* импорт читает внешний файл, и «плохая строка» — это внешнее условие,
  а не баг в коде;
* у вызывающего есть осмысленная реакция: прервать импорт, ничего не публиковать,
  показать пользователю номер строки;
* если сделать unchecked, вызывающий проигнорирует, и импорт молча продолжится
  с половиной данных — худший вариант из возможных.

Это ровно тот случай из задания 2 («отсутствующий файл → checked»), только
контекст стал шире: «источник данных недоступен или повреждён».

## Что делать с другими исключениями внутри

Правило границы: **переводим то, что относится к нашему уровню, и пропускаем
остальное**.

* `NumberFormatException` — «плохое число в поле» → наш, переводим;
* `IOException` при чтении файла — инфраструктурная ошибка → на границе
  импорта превращается в `CourseImportException` с `ErrorCode.SOURCE_UNAVAILABLE`
  (см. `CourseImporter` в задании 14), внутри метода разбора — пролетает насквозь;
* `NullPointerException`, `ClassCastException` — баг → **не ловим вообще**,
  пусть упадёт и упадёт громко (сценарий 5 в `Demo6`).

## Связь с заданием 7 и 15

`CourseImportException` — пример «ошибка как исключение», потому что при импорте
плохая запись означает «операция целиком не выполнена», а не «верни мне -1».

`NumberFormatException` у парсера — пример unchecked-исключения: это не отказ
сервиса, а «ты дал мне не то, что обещал в сигнатуре» (сигнатура `parse(String)`).

А вот «курс не найден» (задание 7) — уже **не** исключение, а `Optional.empty()`:
это нормальный исход поиска, и исключение там заставило бы вызывающего писать
`try/catch` ради ветки «не нашлось».
