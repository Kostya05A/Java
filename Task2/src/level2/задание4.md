# Задание 4. `try-catch-finally`

Код: `Demo4.java`

```bash
./mvnw -q compile
java -cp target/classes level2.Demo4
```

## Порядок выполнения

Порядок всегда один и тот же:

```
try  →  catch (только если было исключение)  →  finally (всегда)
```

`finally` выполняется **всегда**, независимо от того, был ли `return` или `throw`
в `try`. Единственное, что его отменяет, — выход из JVM или убийство потока.
Практически это значит: «написал `finally` — он выполнится, можешь на него
опираться при освобождении ресурсов».

Что при этом происходит с `return`:

```java
private static String returnFromTry() {
    try {
        return "из try";     // значение подготовлено, но ещё НЕ отдано вызывающему
    } finally {
        // выполнится ДО фактического возврата
    }
}
```

Значение не уходит к вызывающему в тот момент, когда написано `return`.
Сначала выполняется `finally`, и только потом значение реально уходит.
Поэтому `finally` может это значение переписать (сценарий 5).

## Таблица: что происходит в каждой комбинации

| В `try` | В `catch` | В `finally` | Что увидит вызывающий |
|---|---|---|---|
| `return v` | — | ничего | `v`. finally выполнился, ничего не изменил |
| `return v` | — | `return w` | `w` — значение из `try` **подменено** |
| `throw E` | ловит `E` | ничего | `catch` отработал, потом finally |
| `throw E` | ловит `E` | `throw F` | `F`. `catch` **не выполнится** вообще: finally стоит между try и catch |
| `throw E` | ловит `E` | `return v` | `v`. Исключение **подавлено** |
| `throw E` | не ловит `E` | ничего | `E` уходит наружу (но finally выполнился) |
| `throw E` | не ловит `E` | `return v` | `v`. Исключение **подавлено** |
| `throw E` | не ловит `E` | `throw F` | `F`. Исходное `E` потеряно |

Две строки стоит запомнить отдельно: `throw` в `finally` и `return` в `finally`
**перехватывают** управление до того, как доберутся до `catch`. То есть `catch`
в том же методе может вообще не выполниться.

## Почему `return` из `finally` запрещён

Это главный трюк задания. Смотрим сценарий 4:

```java
private static void throwFromTryButReturnInFinally() {
    try {
        throw new IllegalStateException("это исключение никто не увидит");
    } finally {
        return;                        // <- подавил исключение
    }
}
```

Вызывающий код:

```java
boolean сработалCatch = false;
try {
    throwFromTryButReturnInFinally();
} catch (IllegalStateException ex) {
    сработалCatch = true;              // сюда не попадём
}
```

Что произошло:

1. в `try` бросилось исключение;
2. JVM начала раскручивать стек и готовилась пробросить его в `catch`;
3. `finally` выполнился и сказал «а я возвращаю значение»;
4. раскрутка стека прервалась — исключение **больше никогда не будет брошено**;
5. `catch` не выполнился, метод «успешно» вернул пустое значение;
6. вызывающий решил, что всё прошло хорошо.

Почему это опасно на практике:

* **Тихое подавление.** Никто не увидит, что была ошибка. Данные могут быть
  записаны наполовину, а лог покажет «операция завершена»;
* **Сложно заметить при чтении.** `finally` стоит в конце метода, глаз
  пробегает его по «хвостовой уборке», а не по ветке управления;
* **Соблазн «сделать метод удобнее».** Реальный пример из жизни: метод
  `closeQuietly` пишут в finally, чтобы освободить ресурс, и по пути добавляют
  `return` — и метод, который должен был сообщить об ошибке записи, молча
  возвращает успех;
* **Ловится только тестами.** Компилятор не предупреждает. Единственная защита —
  правило проекта «в `finally` не бывает ни `return`, ни `throw`».

## Что делать вместо `return` из finally

Три варианта по ситуации:

1. **Нужно подчистить ресурс и уйти с результатом** — вынести логику
   освобождения в отдельный метод и вызвать его в `finally`, а `return`
   оставить в `try`. Если метод освобождения бросает исключение, оно честно
   уйдёт наружу (сценарий 6 — но тогда исходная ошибка теряется, см. ниже);
2. **Нужно не терять исходную ошибку при сбое в finally** — сохранить её
   в `suppressed`. Это ровно то, что делает `try-with-resources`
   (задание 5). Синтаксис вручную:

   ```java
   Throwable primary = null;
   try {
       primary = doWork();            // может бросить
   } catch (Throwable t) {
       primary = t;
       throw t;
   } finally {
       try {
           release();
       } catch (Throwable cleanup) {
           if (primary != null) {
               primary.addSuppressed(cleanup);   // исходная ошибка остаётся главной
           } else {
               throw cleanup;                     // основной ошибки не было - cleanup и есть ошибка
           }
       }
   }
   ```

   Именно этот код компилятор генерирует внутри `try-with-resources`;
3. **Просто не используйте `finally` для управления потоком.** В Java 9+
   `try-with-resources` покрывает почти все реальные случаи, где нужен
   `finally` с гарантированным освобождением.

## Про сценарий 6: исключение из finally

```java
try {
    throw new IllegalStateException("исходная ошибка");
} finally {
    throw new IOException("ошибка при освобождении ресурса");
}
```

Наружу уйдёт `IOException`, а `IllegalStateException` потеряется — он не
автоматически станет `cause` и не попадёт в `suppressed`. Если исходная ошибка
нужна для диагностики, сохранять её надо явно, как в варианте 2 выше.
`try-with-resources` делает это автоматически.
