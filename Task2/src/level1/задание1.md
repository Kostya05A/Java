# Задание 1. Прочитать stack trace

Код: `Demo1.java` (уже написан), теория — в этом файле.

## Как запустить

```bash
./mvnw -q compile
java -cp target/classes level1.Demo1
```

## Что печатает программа

```
Метод 1
Метод 2
Метод 3
ВЫЗОВ ИСКЛЮЧЕНИЙ
В работе...
```

Плюс в вывод идёт stack trace самого исключения (`ex.printStackTrace()`).

## Как читать stack trace

Вывод `printStackTrace()` состоит из трёх частей:

```
java.lang.RuntimeException: ВЫЗОВ ИСКЛЮЧЕНИЙ      <- 1. тип и сообщение
        at Demo1.method4(Demo1.java:20)            <- 2. где ВОЗНИКЛО исключение (первая строка "at")
        at Demo1.method3(Demo1.java:16)            <- 3. путь вызовов (снизу вверх)
        at Demo1.method2(Demo1.java:11)
        at Demo1.method1(Demo1.java:6)
        at Demo1.main(Demo1.java:25)
```

| Что спросили | Где искать | Ответ для этого кода |
|---|---|---|
| Тип | первая строка, до двоеточия | `java.lang.RuntimeException` |
| Сообщение | после `: ` | `ВЫЗОВ ИСКЛЮЧЕНИЙ` |
| Место возникновения | **первая** строка `at` | `Demo1.method4(Demo1.java:20)` |
| Путь вызовов | остальные строки `at`, читаются снизу вверх | `main` → `method1` → `method2` → `method3` → `method4` |

Главное правило: **первая** строка `at` — это где исключение создали (`throw new ...`),
а не где оно "сломалось". Если смотреть на последнюю строку (`main`), кажется, что
виноват `main`, но он только вызвал цепочку.

## "Исправить причину, а не последнюю строку"

Плохая починка — заглушить симптом в `main`:

```java
// Так делать не надо: метод4 всё ещё ломается, мы просто спрятали следы.
try { method1(); } catch (Exception e) { System.out.println("что-то сломалось"); }
```

Правильная починка — спросить "что не так с `method4`?":

```java
private static int divide(int a, int b) {
    if (b == 0) {                                   // <- проверка аргумента ДО операции
        throw new IllegalArgumentException("Делитель не может быть нулём");
    }
    return a / b;
}
```

`catch` в `main` остаётся, но теперь он ловит **конкретный** `IllegalArgumentException`
и знает, что делать (показать пользователю сообщение, записать в лог, выйти с кодом 1).
Ловить `Exception` «на всякий случай» не надо: вы не знаете, что делать с ошибкой,
которую не предусмотрели, и при этом прячете программистские баги (`NullPointerException`,
`ClassCastException`), которые чинить надо в коде, а не проглатывать.
