## Задание 1. `List` и порядок

### Как работает код

**Часть 1 — работа со списком:**
1. Создаётся `ArrayList<String>` — это обёртка над обычным массивом `Object[]`, который автоматически увеличивается при необходимости.
2. `regs.add("alice")` и т.д. — элементы добавляются в конец, их индексы: 0, 1, 2, 3.
3. `regs.add(2, "zoe")` — система сдвигает все элементы с индекса 2 и далее вправо на одну позицию, затем вставляет "zoe" на позицию 2. Получается: `[alice, bob, zoe, carol, dave]`.
4. `regs.remove(1)` — удаляет элемент по индексу 1 ("bob"), сдвигая все последующие влево.
5. Поиск дубликатов: `HashSet<String> seen` хранит уже встреченные элементы. Метод `seen.add(s)` возвращает `false`, если элемент уже есть в множестве — значит, это дубликат.

**Часть 2 — бенчмарк:**
1. Создаются две коллекции по 200 000 элементов.
2. `System.nanoTime()` даёт время с наносекундной точностью.
3. Для `ArrayList.get(i)` — прямой доступ к массиву по смещению, `O(1)`.
4. Для `LinkedList.get(i)` — нужно пройти по связям от головы (или хвоста) до i-го элемента, `O(N)`. При 200 000 случайных запросах это даёт ~15 секунд против ~5 миллисекунд.
5. Обход через for-each использует итератор. У `ArrayList` итератор просто идёт по массиву — элементы лежат в памяти подряд (cache-friendly). У `LinkedList` каждый элемент — отдельный объект со ссылкой на следующий — проходы по памяти, cache miss.

### Ключевые моменты
- **`ArrayList`** — динамический массив, быстрый произвольный доступ, медленная вставка в середину (сдвиг).
- **`LinkedList`** — двусвязный список, быстрая вставка/удаление по известной позиции, медленный доступ по индексу.
- **Cache locality** — непрерывный массив быстрее обходить из-за предвыборки процессором.

## Задание 2. `Set` и уникальность

### Как работает код

1. `record CourseCode(String subject, int number)` — Java автоматически генерирует:
   - `equals`: сравнивает оба поля.
   - `hashCode`: вычисляется по `subject` и `number` через `Objects.hash`.
   - `toString`, конструктор, геттеры.

2. `LinkedHashSet` — это комбинация:
   - **Хеш-таблицы** (для `O(1)` `add/contains`).
   - **Двусвязного списка** (для сохранения порядка вставки).
   
   При добавлении элемента:
   - Вычисляется `hashCode`.
   - Определяется бакет (ячейка) в хеш-таблице.
   - Если в бакете уже есть равный элемент (`equals` возвращает `true`) — дубликат игнорируется.
   - Иначе элемент добавляется в бакет И в конец связного списка.

3. Когда в `LinkedHashSet` передаётся список с дубликатами, повторяющиеся элементы просто не добавляются, а порядок первых появлений сохраняется.

### Почему важен контракт equals/hashCode

Хеш-таблица работает так:
1. По `hashCode` находится бакет.
2. В бакете сравниваются элементы через `equals`.

Если два объекта равны по `equals`, но имеют разный `hashCode`:
- Они попадут в разные бакеты.
- `contains` не найдёт дубликат, потому что даже не будет искать в "неправильном" бакете.

Если `hashCode` одинаков у неравных объектов — это нормально (коллизия), хеш-таблица разрешит её через `equals`.

## Задание 3. `Map` и индекс

### Как работает код

1. `HashMap<Integer, Course>` — хеш-таблица, где ключ — ID курса, значение — сам курс.
2. Для каждого входящего курса:
   - `putIfAbsent(id, course)` проверяет, есть ли уже такой ключ.
   - Если ключа нет — вставляет и возвращает `null`.
   - Если ключ есть — возвращает старое значение, не перезаписывая.
3. По возвращённому значению определяется, был ли дубликат.

### Разница между методами

- **`get(k)`**: один lookup. Возвращает `null`, если ключа нет. Но `null` может быть и легитимным значением! Поэтому `get` не всегда отличает "нет ключа" от "значение null".
- **`containsKey(k)`**: отдельный lookup. Отвечает только на вопрос "есть ли ключ".
- **`putIfAbsent(k, v)`**: один lookup, атомарно (для однопоточного случая). Если ключа нет — вставляет, возвращает `null`. Если есть — возвращает старое значение.
- **`computeIfAbsent(k, f)`**: как `putIfAbsent`, но значение вычисляется лениво через функцию `f`. Полезно, когда построение значения дорогое (например, создание сложного объекта).

**Почему `putIfAbsent` лучше, чем `if (!containsKey) put`:**
- Один lookup вместо двух.
- В `ConcurrentHashMap` — атомарная операция.

## Задание 4. Очередь ожидания

### Как работает код

`ArrayDeque` — это массив с двумя указателями (голова и хвост), который циклически используется. Это быстрее `LinkedList` для очереди, так как нет накладных расходов на создание узлов.

**Пары методов:**

| Операция | Бросает исключение | Возвращает спец-значение |
|----------|-------------------|--------------------------|
| Добавить | `add(e)` → `IllegalStateException` | `offer(e)` → `false` |
| Извлечь | `remove()` → `NoSuchElementException` | `poll()` → `null` |
| Посмотреть | `element()` → `NoSuchElementException` | `peek()` → `null` |

**Когда что использовать:**
- Если пустая очередь — это **нормальная ситуация** (например, обработка входящих задач), используйте `poll`/`peek`.
- Если пустая очередь — это **ошибка** (нарушение инварианта), используйте `remove`/`element`.

**Для `ArrayDeque`** (не ограниченной по размеру) `add` и `offer` работают одинаково — очередь никогда не "отказывается" принимать элемент. Разница важна для bounded-очередей, например `ArrayBlockingQueue`.

## Задание 5. Безопасное удаление при обходе

### Как работает код

**Почему возникает `ConcurrentModificationException`:**
- Когда создаётся итератор, он запоминает `modCount` — счётчик структурных модификаций коллекции.
- При каждом вызове `next()` итератор проверяет: не изменился ли `modCount`.
- Если `list.remove(s)` вызван напрямую, `modCount` увеличивается, но итератор об этом не знает → при следующем `next()` бросается исключение.

**Исправление через `Iterator.remove()`:**
- `it.remove()` удаляет последний возвращённый элемент И обновляет `expectedModCount` итератора.
- Поэтому итератор "знает" об изменении и не бросает исключение.

**Исправление через `removeIf`:**
- У `ArrayList` метод `removeIf` переопределён: он не использует итератор, а делает один проход по массиву, сдвигая элементы.
- Это быстрее и безопаснее, чем итератор.
- В базовой реализации `Iterable.removeIf` используется итератор, но для `ArrayList` есть оптимизация.

**Почему копирование — не default:**
- `new ArrayList<>(list)` — это `O(N)` памяти и времени.
- Копия может устареть, если оригинал меняется в другом потоке.
- `removeIf` у `ArrayList` работает за `O(N)` без копий — просто сдвигает элементы.
- Копирование оправдано только когда нужна **снимковая семантика**: вы хотите обрабатывать состояние списка на момент начала итерации, игнорируя последующие изменения.

## Задание 6. Первый generic-тип `Result<T>`

### Как работает код

1. **Параметр типа `T`**: при создании `Result<Integer>` компилятор подставляет `Integer` вместо `T` во всех местах класса.
2. **Приватный конструктор**: объекты создаются только через фабрики `success` и `failure`. Это гарантирует, что инварианты всегда выполняются.
3. **Инварианты**:
   - Если `ok == true`, то `value != null`.
   - Если `ok == false`, то `error != null`.
   - Проверяются в конструкторе — если нарушены, бросается `IllegalStateException`.
4. **`getValue`/`getError`**: бросают исключение, если вызываются в неправильном состоянии. Это лучше, чем возврат `null`, потому что ошибка обнаруживается сразу.
5. **Метод `map`**: применяет функцию к значению, если это успех; иначе пробрасывает ошибку. Сигнатура `Function<? super T, ? extends U>` — это PECS: функция может принимать надтип `T` и возвращать подтип `U`.

### Compile-time защита

```java
Result<Integer> r1 = Result.success(42);
Result<String>  r2 = Result.failure("boom");
r1 = r2; // Ошибка компиляции!
```

Компилятор знает, что `r1` — это `Result<Integer>`, а `r2` — `Result<String>`. Они несовместимы, даже если оба являются `Result<?>`.

Без дженериков (raw types):
```java
Result r1 = Result.success(42);
Result r2 = Result.failure("boom");
r1 = r2; // Компилируется! Но это ошибка.
```

## Задание 7. Generic-методы

### Как работает код

**`firstOrThrow(List<T>)`:**
- Параметр типа `T` выводится из типа аргумента.
- Если список пуст или `null` — бросается `NoSuchElementException`.
- Иначе возвращается первый элемент.

**`swap(List<T>, int, int)`:**
- Меняет местами элементы по индексам.
- Проверяет границы — иначе `IndexOutOfBoundsException`.
- Использует временную переменную типа `T`.

**`indexBy(List<T>, Function<? super T, ? extends K>)`:**
- Строит `LinkedHashMap` (сохраняет порядок вставки).
- Для каждого элемента вычисляет ключ через `keyFn`.
- `putIfAbsent` проверяет, нет ли уже такого ключа.
- Если есть — бросается `IllegalArgumentException` с описанием конфликта.
- PECS в сигнатуре функции: `? super T` позволяет передавать функции, принимающие надтипы; `? extends K` — возвращающие подтипы.

### Почему явная обработка конфликта лучше молчаливой перезаписи

Если два элемента имеют одинаковый ключ, это обычно означает ошибку в данных или логике. Молчаливая перезапись скрывает проблему — программа работает, но с неправильными данными. Явное исключение сразу указывает на источник ошибки.

## Задание 8. Ограничение типа

### Как работает код

**Сигнатура `<T extends Comparable<? super T>>`:**
- `T extends Comparable<...>` — `T` должен реализовывать `Comparable`.
- `? super T` — параметр `Comparable` может быть `T` или его надтипом.

**Зачем `? super T`:**

Рассмотрим иерархию:
```java
class A implements Comparable<A> { ... }
class B extends A { ... } // B не реализует Comparable напрямую
```

Без `? super T`:
```java
<T extends Comparable<T>> T max(...)
```
Вызов `max(List<B>)` не скомпилируется, потому что `B` не реализует `Comparable<B>` — он наследует `Comparable<A>`.

С `? super T`:
```java
<T extends Comparable<? super T>> T max(...)
```
`B` реализует `Comparable<A>`, а `A` — это `super B`. Поэтому `max(List<B>)` компилируется и работает.

**Алгоритм `max`:**
1. Берёт первый элемент как текущий максимум.
2. Проходит по остальным, сравнивая через `compareTo`.
3. Если `x.compareTo(best) > 0` — `x` больше, обновляет `best`.
4. Возвращает `best`.

## Задание 9. PECS на практике

### Как работает код

**Метод `copy`:**
```java
public static <T> void copy(List<? extends T> src, List<? super T> dst)
```

- `? extends T` — `src` может быть списком `T` или любого подтипа `T`. Мы **читаем** из него, поэтому нам важно, что элементы являются `T` (или его подтипами, что совместимо).
- `? super T` — `dst` может быть списком `T` или любого надтипа `T`. Мы **пишем** в него, поэтому нам важно, что он может принимать `T` (или его надтипы, что совместимо).

**Почему нельзя добавить в `List<? extends Course>`:**
- Компилятор не знает точный тип: это может быть `List<MathCourse>`, `List<PhysCourse>` и т.д.
- Если бы мы могли добавить `Course`, то в `List<MathCourse>` оказался бы `PhysCourse` — нарушение инварианта.
- Поэтому `add` запрещён (кроме `null`).

**Что можно читать из `List<? super Course>`:**
- Это может быть `List<Course>`, `List<Object>`, `List<Serializable>` и т.д.
- Единственный тип, гарантированно присутствующий во всех этих списках — `Object`.
- Поэтому читать можно только как `Object`.

**Принцип PECS:**
- **Producer Extends**: если вы читаете из коллекции, используйте `? extends T`.
- **Consumer Super**: если вы пишете в коллекцию, используйте `? super T`.
- Если и то, и другое — не используйте wildcard, используйте точный тип `T`.

## Задание 10. Контракт ключа

### Как работает код

**Класс `Course`:**
- `equals` сравнивает только `id`.
- `hashCode` намеренно ошибочно зависит от `id` И `description`.

**Сценарий:**
1. Создаётся `Course(1, "Algo", "intro")`.
2. Вычисляется `hashCode`: зависит от `id=1` и `description="intro"`.
3. Объект добавляется в `HashSet` — попадает в бакет, соответствующий этому hash.
4. `contains(c)` возвращает `true` — объект найден.
5. Меняется `c.description = "advanced"`.
6. Теперь `hashCode` другой (зависит от "advanced"), но объект всё ещё в старом бакете!
7. `contains(c)` вычисляет новый hash, ищет в новом бакете — не находит. Возвращает `false`.

**Почему это проблема:**
- Объект физически есть в множестве, но "потерян".
- Его нельзя удалить, найти, заменить.
- Это утечка памяти и логическая ошибка.

**Правило:**
- `hashCode` должен зависеть ровно от тех полей, что и `equals`.
- Эти поля должны быть **final** или **эффективно неизменяемыми**.
- Если нужно изменить поле, участвующее в hash — удалите объект из коллекции, измените, добавьте обратно.

## Задание 11. Выбор по нагрузке

### Как работает код

Для каждого сценария выбрана оптимальная реализация:

1. **Каталог по ID → `HashMap`:**
   - Ключ — `Integer` (ID курса), значение — `Course`.
   - `get`, `put`, `containsKey` — `O(1)` в среднем.
   - Порядок не важен, память — средняя (хеш-таблица с load factor 0.75).

2. **Leaderboard → `TreeSet` с компаратором:**
   - Компаратор: сначала по score (убывание), затем по имени.
   - `add`, `remove`, `first`, `last` — `O(log N)`.
   - Элементы всегда отсортированы, память — высокая (красно-чёрное дерево, каждый узел — отдельный объект с ссылками).

3. **Очередь → `ArrayDeque`:**
   - `offer`, `poll`, `peek` — `O(1)` амортизированное.
   - Память — низкая (компактный массив, циклический буфер).
   - Порядок — FIFO.

4. **Теги с порядком → `LinkedHashSet`:**
   - `add`, `contains` — `O(1)`.
   - Сохраняет порядок вставки.
   - Память — средняя (хеш-таблица + связный список).

5. **Диапазонный поиск → `TreeMap`:**
   - `get`, `put` — `O(log N)`.
   - `subMap`, `headMap`, `tailMap` — `O(log N + K)`, где K — размер диапазона.
   - `floorKey`, `ceilingKey` — `O(log N)`.
   - Порядок — по ключу.

6. **Доступ по индексу → `ArrayList`:**
   - `get(i)` — `O(1)`.
   - `add` в конец — `O(1)` амортизированное.
   - Вставка в середину — `O(N)` (сдвиг элементов).
   - Память — низкая (непрерывный массив, cache-friendly).

## Задание 12. Generic repository

### Как работает код

**Интерфейс `Repository<ID, T>`:**
- Два параметра типа: `ID` (тип ключа) и `T` (тип сущности).
- Методы: `save`, `findById`, `findAll`, `deleteById`.

**Реализация `InMemoryRepository`:**
- Использует `LinkedHashMap<ID, T>` — сохраняет порядок вставки.
- **`save`**: проверяет `null` через `Objects.requireNonNull`, затем `put`. Если ключ уже есть — перезапись (upsert).
- **`findById`**: проверяет `null`, вызывает `get`. Если результат `null` — бросает `NoSuchElementException`. Это лучше, чем возврат `null`, потому что явно сигнализирует об ошибке.
- **`findAll`**: возвращает `List.copyOf(store.values())` — **неизменяемую копию**. Это защищает внутреннюю коллекцию: если клиент изменит возвращённый список, внутреннее состояние не пострадает.
- **`deleteById`**: проверяет `null`, вызывает `remove`. Возвращает `true`, если элемент был удалён.

**Почему два файла:**
- В Java public-тип должен быть в файле с тем же именем.
- `Repository` — public interface → `Repository.java`.
- `InMemoryRepository` — public class → `InMemoryRepository.java`.

## Задание 13. Обратный индекс

### Как работает код

**Два индекса:**
1. `Map<String, Set<Integer>> idx`: тег → множество ID курсов.
2. `Map<Integer, Set<String>> courseTags`: ID курса → множество тегов.

**`addCourse(courseId, tags)`:**
1. `courseTags.putIfAbsent(courseId, new HashSet<>())` — создаёт пустое множество тегов для курса, если его нет.
2. Для каждого тега:
   - Добавляет тег в `courseTags.get(courseId)`.
   - `idx.computeIfAbsent(tag, k -> new HashSet<>()).add(courseId)` — создаёт пустое множество курсов для тега, если его нет, и добавляет courseId.

**`removeCourse(courseId)`:**
1. Удаляет курс из `courseTags`, получая множество его тегов.
2. Для каждого тега:
   - Удаляет courseId из `idx.get(tag)`.
   - Если множество стало пустым — удаляет тег из `idx` (чтобы память не текла).

**`intersect(tags)`:**
1. Если `tags` пуст — возвращает пустое множество.
2. Берёт первый тег, получает множество курсов из `idx`.
3. Для каждого следующего тега:
   - `acc.retainAll(idx.getOrDefault(tag, Set.of()))` — оставляет только курсы, которые есть в обоих множествах.
   - Если `acc` стало пустым — прерывает цикл (оптимизация).
4. Возвращает `acc`.

**Почему два индекса:**
- Без `courseTags` удаление курса потребовало бы сканировать все теги в `idx` — `O(|tags| * |idx|)`.
- С `courseTags` удаление — `O(|tags|)`, где `|tags|` — число тегов у курса.

## Задание 14. Ограниченный LRU-кэш

### Как работает код

**`LinkedHashMap` с `accessOrder=true`:**
- По умолчанию `LinkedHashMap` сохраняет порядок вставки.
- С `accessOrder=true` — при каждом `get` или `put` элемент перемещается в конец (становится "самым свежим").
- Первый элемент — "самый старый" (наименее недавно использованный).

**`removeEldestEntry`:**
- Этот метод вызывается после каждой вставки (`put`).
- Если возвращает `true` — самый старый элемент удаляется.
- В нашей реализации: возвращает `true`, если `size() > capacity`.

**`get(key)`:**
- Проверяет `null` через `Objects.requireNonNull`.
- Вызывает `map.get(key)` — это перемещает элемент в конец (обновляет недавность).
- Возвращает значение или `null` (если ключа нет).

**`put(key, value)`:**
- Проверяет `null` для ключа и значения.
- Вызывает `map.put(key, value)` — это добавляет или обновляет элемент, перемещая его в конец.
- Если размер превысил ёмкость — `removeEldestEntry` удаляет самый старый элемент.

**Пример работы:**
1. `put("a", 1)`, `put("b", 2)`, `put("c", 3)` — порядок: a, b, c.
2. `get("a")` — "a" перемещается в конец. Порядок: b, c, a.
3. `put("d", 4)` — добавляется "d", размер становится 4 > 3. Удаляется самый старый — "b". Порядок: c, a, d.

**Почему `null` запрещён:**
- `LinkedHashMap` разрешает один `null`-ключ и сколько угодно `null`-значений.
- Но `get(key)` возвращает `null` как при промахе, так и если значение действительно `null`.
- Чтобы избежать неоднозначности, запрещаем `null` полностью.

## Задание 15. Планировщик prerequisites

### Как работает код

**Граф зависимостей:**
- `Map<T, Set<T>> prereqs`: вершина → множество её пререквизитов.
- Ребро `course → prerequisite` означает "course требует prerequisite".

**`addEdge(course, prerequisite)`:**
- Если вершин нет — добавляет их (через `addVertex`).
- Добавляет `prerequisite` в множество пререквизитов `course`.

**`topologicalOrder` (алгоритм Кана):**
1. Подсчитывает входящие степени (`indeg`): для каждой вершины — число пререквизитов.
2. Находит все вершины с `indeg == 0` (нет пререквизитов) — добавляет в очередь `ready`.
3. Пока очередь не пуста:
   - Извлекает вершину `v`.
   - Добавляет в `order`.
   - Для каждой вершины `dep`, которая зависит от `v` (т.е. `v` — пререквизит `dep`):
     - Уменьшает `indeg[dep]` на 1.
     - Если `indeg[dep] == 0` — добавляет `dep` в очередь.
4. Если `order.size() != indeg.size()` — есть цикл.

**`findCycle` (DFS):**
1. Для каждой вершины, если она ещё не обработана, запускает DFS.
2. Поддерживает:
   - `done` — полностью обработанные вершины.
   - `onStack` — вершины в текущем пути рекурсии.
   - `path` — текущий путь (для восстановления цикла).
3. При обходе соседей:
   - Если сосед в `onStack` — найден цикл. Восстанавливает путь от соседа до соседа.
   - Если сосед не в `done` — рекурсивный вызов.
4. После обработки вершины: удаляет из `onStack` и `path`, добавляет в `done`.

**Почему `LinkedHashMap` и `LinkedHashSet`:**
- Они сохраняют порядок вставки.
- При одинаковом вводе порядок итерации одинаков → результат детерминирован.
- `HashMap` и `HashSet` не гарантируют порядок → результат может меняться от запуска к запуску.

**Сложность:**
- Алгоритм Кана: `O(V + E)` — каждый узел и ребро обрабатываются один раз.
- DFS: `O(V + E)` — аналогично.
- Память: `O(V + E)` для хранения графа и вспомогательных структур.

**Пример:**
- Рёбра: `Algorithms → DataStructures → Programming`, `ML → Algorithms`.
- Входящие степени: `Programming=0`, `DataStructures=1`, `Algorithms=1`, `ML=1`.
- Очередь: `[Programming]`.
- Извлекаем `Programming`, уменьшаем `indeg[DataStructures]` до 0, добавляем в очередь.
- Извлекаем `DataStructures`, уменьшаем `indeg[Algorithms]` до 0, добавляем.
- Извлекаем `Algorithms`, уменьшаем `indeg[ML]` до 0, добавляем.
- Извлекаем `ML`.
- Порядок: `[Programming, DataStructures, Algorithms, ML]`.
