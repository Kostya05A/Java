# Задание 5. Try-with-resources

Код: `LoggableResource.java` (тестовый ресурс) и `Demo5.java` (шесть сценариев).

```bash
./mvnw -q compile
java -cp target/classes level2.Demo5
```

## Зачем это нужно

`finally` из задания 4 решает задачу «освободить ресурс», но вручную. И почти
всегда пишется неправильно — забывают `close()`, или пишут `return`/`throw`
в `finally` (разбор в задании 4), или теряют вторую ошибку.

`try-with-resources` (TWR) делает это автоматически и в правильном порядке:

```java
try (LoggableResource resource = new LoggableResource("A", log)) {
    resource.use("читаем");
    resource.use("считаем");
}   // <- close() вызывается тут, и даже если внутри было исключение
```

## Что именно делает компилятор

TWR — это не отдельная конструкция рантайма, а **синтаксический сахар**: компилятор
разворачивает его в `try/finally` с правильной обработкой. Механика:

1. ресурс объявляется в скобках `try`, его область видимости — только блок `try`;
2. в конце блока (любым путём: обычный выход, `return`, `throw`) вызывается `close()`;
3. **если тело `try` завершилось исключением И `close()` тоже бросил** — второй
   вызов не перекрывает первый, а добавляется в `getSuppressed()` первого;
4. **если тело завершилось нормально, а `close()` бросил** — наружу уходит
   исключение из `close()`;
5. при нескольких ресурсах закрытие идёт в **обратном** порядке (как стек):
   открыли `Первый`, `Второй` → закрыли `Второй`, `Первый` (сценарий 5);
6. `close()` вызывается **до** того, как исключение долетит до внешнего `catch`
   (сценарий 4 — в логе `close` стоит раньше обработки).

## Сценарий 3: ошибка и в работе, и в close (главный)

```java
try (LoggableResource resource = new LoggableResource("C", log, true)) { // true = close упадёт
    resource.use("пишем");
    throw new IOException("сбой записи данных");
}
```

Вывод:

```
ОСНОВНОЕ исключение: IOException: сбой записи данных
SUPPRESSED (1):
  - IOException: C: сбой при закрытии (flush не прошёл)
```

Что это значит и зачем так:

* **основная** ошибка та, из тела `try` — она определяет, что пошло не так
  с бизнес-операцией;
* **ошибка закрытия** (flush не прошёл, файл не записался на диск) не вытесняет
  основную, а живёт в `getSuppressed()`;
* ничего не потеряно: `getSuppressed()[0].getMessage()` даёт деталь про flush,
  а `getCause()` / основное сообщение — про исходную операцию.

Сравните с наивным `finally` (задание 4, сценарий 6): там исключение из `finally`
**заменяло** исходное, и `IllegalStateException("исходная ошибка")` исчезал
бесследно. TWR решает ровно эту проблему.

`getSuppressed()` — обычный API:

```java
for (Throwable s : ex.getSuppressed()) {
    log.warn("дополнительная ошибка при освобождении ресурса", s);
}
```

Их может быть несколько (по одной на каждый упавший `close()`), и в лог их
стоит писать все.

## Сценарий 2: ошибка только в теле

```
поймали снаружи: IOException: сбой чтения данных
suppressed у этого исключения: []
```

Ресурс закрылся (в логе `B: close` есть), ошибка ушла наружу обычным порядком,
`suppressed` пуст — добавлять нечего, `close()` не падал.

## Сложность, которую TWR создаёт

`AutoCloseable.close()` объявлен как `throws Exception`. Даже если конкретная
реализация **никогда** не бросит, компилятор требует `catch` или `throws` в
каждом месте использования — он не знает ваших намерений. В `Demo5` поэтому
везде `catch (Exception ex)`, и в комментариях стоит «сюда не попадём».

Два способа это смягчить:

1. **Сузить `throws` в своей реализации** — нельзя выбросить больше, чем
   разрешено интерфейсом, и `IOException` ⊂ `Exception`, поэтому так можно:

   ```java
   @Override
   public void close() throws IOException { ... }
   ```

   Тогда вызывающий ловит `IOException`, а не `Exception`. Заметьте: в
   `LoggableResource` оставлено `throws Exception` **намеренно** — так видно
   разницу в поведении компилятора для `catch (Exception)` и `catch (IOException)`;
2. **Использовать `java.io.Closeable`**, у которого `close() throws IOException`
   — узкий, «честный» контракт.

## Ещё две возможности

* **Список ресурсов.** Несколько ресурсов через `;` в одном `try` (сценарий 5).
  Вложенность кода не растёт, порядок закрытия — обратный.
* **Существующая переменная (Java 9+).** `try (resource) {}` работает и с
  переменной, объявленной раньше (сценарий 6). Требует, чтобы переменная была
  `final` или `effectively final` (её не переприсваивают), иначе компилятор
  не сможет доказать, что это тот же самый ресурс. Область видимости уже, чем
  у варианта в скобках, — использовать, когда ресурс нужен до `try` или в `catch`.

## Правила, которые стоит запомнить

1. В `finally` не бывает `return` и `throw` (задание 4);
2. Ресурс, который надо закрыть, объявляется в `try (...)`, а не в `finally`;
3. Никогда не пишите `catch (Exception e) { }` внутри `finally` «на всякий случай»
   — это ровно тот код, который прячет диагностику;
4. Ресурс должен быть идемпотентным на `close()` (у нас он такой: повторный
   `close()` просто пишет в лог), потому что в цепочках вложенных ресурсов
   `close()` может быть вызван неожиданно.
