# Задание 15. Публичный слой: ни одного исключения наружу

Код: `src/level5/CourseHub.java`, `OperationResult.java`,
`src/domain/ErrorCode.java`, тесты: `test/level5/CourseHubContractTest.java`

```bash
./mvnw test -Dtest=CourseHubContractTest
java -cp target/classes level5.CourseHub
```

## Идея

К этому моменту внутри системы живут четыре разных вида отказа:

* доменный отказ — значение (`EnrollmentResult` со статусом `REJECTED`);
* доменный отказ — исключение (`EnrollmentRejectedException`);
* инфраструктурный отказ импорта — `ImportAbortedException`;
* инфраструктурный отказ импорта — `SourceUnavailableException`;
* плюс `IllegalArgumentException` из `CourseCode` и `Course`.

Если всё это дойдёт до клиента, он начнёт зависеть от внутренней
структуры приложения. `CourseHub` — граница, на которой внутренние
типы превращаются в **стабильный код**.

## Контракт

```java
public OperationResult enroll(long studentId, String rawCourseCode)
public Optional<Course> findCourse(String rawCourseCode)
public OperationResult importCourses(Path file)
public OperationResult cancelEnrollment(long studentId, String rawCourseCode)
```

Три правила:

1. **Ни одно исключение не выходит наружу.** Не `RuntimeException`,
   не `IOException`, не `Error`. У клиента нет `try/catch`.
2. **Всегда есть код.** `ErrorCode` — единственный язык, на котором
   публичный слой говорит об отказах.
3. **Найдено/не найдено — не отказ.** `findCourse` возвращает `Optional`,
   потому что «курса нет» — это ответ на вопрос, а не сбой.

## Перевод на границе

```java
public OperationResult enroll(long studentId, String rawCourseCode) {
    CourseCode code;
    try {
        code = CourseCode.of(rawCourseCode);
    } catch (IllegalArgumentException ex) {
        // Невалидный код от клиента - это не баг, а отказ.
        // Внутри был unchecked, наружу уходит значение.
        return OperationResult.failure(ErrorCode.COURSE_NOT_FOUND,
                "Код курса не распознан: " + rawCourseCode);
    }

    EnrollmentResult result = enrollment.enroll(studentId, code);

    if (result.isAccepted()) {
        return OperationResult.success("Студент " + studentId + " зачислен в " + code);
    }
    if (result.status() == EnrollmentResult.Status.WAITLISTED) {
        return OperationResult.success(ErrorCode.NO_SEATS,
                "Свободных мест нет, " + studentId + " в листе ожидания курса " + code);
    }
    return OperationResult.failure(result.reason(),
            "Зачисление невозможно: " + result.reason().clientMessage());
}
```

Тут видно главное: `CourseHub` **не переинтерпретирует** исход. Он получил
`ErrorCode` из домена и передал его клиенту. Любая новая причина отказа
в домене автоматически доедет до клиента — если её есть в `ErrorCode`.
Если её нет, компилятор напомнит (см. задание 13 про полноту `switch`).

### Лист ожидания — успех с кодом

```java
OperationResult.success(ErrorCode.NO_SEATS, "Свободных мест нет, ...")
```

`success = true`, но код — `NO_SEATS`. Формально операция выполнена
(заявка принята и поставлена в лист), фактически зачисления не было.
Один флаг здесь не смог бы выразить оба факта, а молчаливый `success=true`
вводил бы в заблуждение: клиент показал бы «вы зачислены».

## Код, а не текст

```java
public enum ErrorCode {
    OK("Операция выполнена"),
    COURSE_NOT_FOUND("Курс не найден"),
    COURSE_CLOSED("Курс закрыт для зачисления"),
    ...
}
```

| Что меняем | Можно? | Почему |
|---|---|---|
| Текст в `clientMessage()` | свободно | это локализация, клиент её подставит в свой интерфейс |
| `toString` у внутренних классов | свободно | деталь логов |
| Значение `ErrorCode` | только с новым значением | это контракт: клиент пишет `switch (code)` |
| Сообщение `OperationResult` | свободно | клиент ориентируется на код |

Пример из этого проекта: `Reason` в `EnrollmentRejectedException` вырос с
четырёх значений до пяти (`COURSE_NOT_FOUND`), потому что таблица решений
стала полной. Это внутренняя правка — публичный `ErrorCode` не изменился.

### Зачем в перечне есть `OK`

Клиенту нужен один полный набор исходов, а не два разных способа узнать
об успехе. Без `OK` пришлось бы спрашивать сначала `result.success()`, и только
потом — код; `OK` позволяет всегда смотреть на код и покрыть им оба случая:

```java
if (result.code() == ErrorCode.OK) {
    // штатный успех
} else if (result.code() == ErrorCode.NO_SEATS) {
    // заявка принята в лист ожидания
}
```

Поэтому «успех» здесь — это не отсутствие ошибки, а конкретное значение,
которое можно перечислить в `switch`.

## Что не утекает

```java
@Test
@DisplayName("имена внутренних исключений не попадают в результат")
void noInternalTypeNamesInResult() { ... }
```

Проверяется, что в результате нет строк `ImportAbortedException`,
`SourceUnavailableException`, `NoSuchFileException`, `IllegalArgumentException`.
Причина простая: однажды внутренний класс переименуют, клиент напечатает
на экране `IllegalArgumentException: не удалось преобразовать тип
java.lang.Object` — и это станет пользовательским багом, найти который
можно только по скриншоту.

Детали уходят в лог, а не в ответ:

```java
} catch (ImportAbortedException ex) {
    logInternal("IMPORT_ABORTED", ex);
    return OperationResult.failure(ErrorCode.MALFORMED_RECORD,
            "Импорт прерван: запись №" + ex.recordNumber() + " не соответствует формату");
}
```

Пользователю — номер строки (он полезен: он может сам посмотреть файл),
но не путь к файлу, не `getCause()` и не стектрейс. Тест
`userMessageLeaksNothing` требует, чтобы в сообщении не было ни
`passwd`, ни `/etc`.

## Мёртвые коды

```java
@Test
@DisplayName("все значения ErrorCode используются хотя бы раз")
void everyCodeIsReachable() {
    EnumSet<ErrorCode> reachable = EnumSet.noneOf(ErrorCode.class);
    reachable.add(hub.enroll(1, "мусор").code());
    ...
    assertEquals(EnumSet.allOf(ErrorCode.class), reachable);
}
```

Код, который никогда не выдаётся, — это мусор в контракте. Через
полгода его удалят «на всякий случай», а потом, когда он понадобится,
добавят заново — и окажется, что у клиента на него нет обработки.
Значит, лишние значения в `ErrorCode` надо удалять сразу.

## Тесты контракта

| Тест | Что защищает |
|---|---|
| `enrollNeverThrows` (параметры) | никакой вход не приводит к исключению |
| `importNeverThrows` | включая `null`-подобные и системные пути |
| `resultIsNeverNull` | клиент всегда получает объект |
| `everyCodeHasClientMessage` | у каждого кода есть текст |
| `userMessageLeaksNothing` | нет путей и внутренних деталей |
| `noInternalTypeNamesInResult` | нет имён внутренних классов |
| `everyCodeIsReachable` | нет мёртвых кодов |
| `failedImportChangesNothing` | откат виден и на публичном слое |
| `recordHasValueEquality` | `record` даёт сравнение по значению |

Проверка `assertDoesNotThrow` на параметризованном наборе входов
(`"мусор"`, `""`, `"/"`, `нет-такого.csv`) — самая дешёвая защита
контракта: одно утверждение, а закрывает целый класс проблем
с тем, что метод внезапно бросит на неожиданных данных.

## Итоговая карта: где что обрабатывается

| Слой | Отказ | Форма |
|---|---|---|
| домен | курс закрыт, нет пререквизита, дубликат | `ErrorCode` в `EnrollmentResult` |
| домен | границы 10..40 ч | `IllegalArgumentException` (unchecked) |
| импорт | плохая запись | `ImportAbortedException` (checked) + откат |
| импорт | нет файла | `SourceUnavailableException` (checked) + код |
| публичный слой | всё вышеперечисленное | `OperationResult` + `ErrorCode` |
| публичный слой | курс не найден при поиске | `Optional.empty()` |

## Сводка

| Решение | Причина |
|---|---|
| Ни одного исключения наружу | Клиент не должен знать про внутренние типы |
| `ErrorCode` вместо текста | Текст меняют, код — часть контракта |
| `OperationResult.success(code, msg)` | Успех может быть с важным кодом (`NO_SEATS`) |
| Детали в лог, не в ответ | Путь к файлу и `cause` — не для пользователя |
| Тест «код не содержит имени исключения» | Защита от утечки внутренних имён |
| Тест «все коды достижимы» | Нет мёртвых значений в контракте |
