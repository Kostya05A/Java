# Задание 7. Ошибка как значение или исключение

Код: `CourseService.java` (четыре операции), `PaymentGatewayException.java`,
`Demo7.java` (запуск).

```bash
./mvnw -q compile
java -cp target/classes level2.Demo7
```

## Решения

| Операция | Выбор | Почему |
|---|---|---|
| `findCourse` | `Optional<Course>` | Отсутствие — штатный исход поиска, а не сбой |
| `parseCourse` | типизированный `ParseResult` | Причин отказа много, надо различать |
| `enroll` | типизированный `EnrollmentResult` | Отказ зачисления — бизнес-исход, не поломка |
| `calculatePrice` | checked `PaymentGatewayException` | Внешний отказ, у вызывающего есть политика |

## 1. `findCourse` → `Optional`

```java
public Optional<Course> findCourse(String rawCode) {
    Course course = switch (rawCode == null ? "" : rawCode.trim().toUpperCase()) {
        case "JAVA-101" -> Course.of("JAVA-101", "Основы Java", 30);
        case "WEB-200"   -> Course.of("WEB-200", "Веб-разработка", 25);
        default -> null;
    };
    return Optional.ofNullable(course);
}
```

Ключевое: **«не нашлось» — это ответ на вопрос, а не ошибка**. Вызовший
`findCourse` именно это и спрашивал. Бросать исключение значило бы заставить
писать `try/catch` ради обычной ветки:

```java
// так писать не надо
try {
    Course course = service.findCourse(code);
    render(course);
} catch (CourseNotFoundException e) {
    renderEmptyState();
}
```

`Optional` делает разбор обязательным — `orElse` / `orElseThrow` / `ifPresent`
всегда придётся вызвать, компилятор не даст забыть:

```java
String title = missing.map(Course::title).orElse("курс не найден");
```

**Граница.** Внутри метода `Optional` — только «нашлось / не нашлось».
Как только пустой `Optional` дошёл до слоя, который обязан что-то сделать
(отдать 404, записать в очередь), его превращают в исключение или в
`ResponseStatusException`. Держать `Optional` в полях объекта нельзя —
это «Optional в полях» (antipattern): значение постоянно отсутствует,
и каждый доступ требует проверки.

## 2. `parseCourse` → типизированный результат

Почему не `Optional`: у разбора **несколько разных** причин отказа
(`MALFORMED_FORMAT`, `INVALID_CODE`, `EMPTY_TITLE`, `INVALID_HOURS`,
`HOURS_OUT_OF_RANGE`). `Optional` различает только два состояния, и вызывающий
не сможет сказать пользователю, что именно исправлять.

Почему не исключение: разбор вызывают в цикле (импорт файла на 50 000 строк).
Исключение на каждой плохой строке превращается в:

```java
for (String line : lines) {
    try {
        drafts.add(parseCourse(line));
    } catch (ParseException e) {
        errors.add(e);        // а теперь мы всё равно пишем обработчик,
    }                        // который просто собирает список ошибок
}
```

То есть исключение используется как «исключительный способ вернуть значение».
Форма `ParseResult` делает то же самое, но без control flow:

```java
ParseResult result = service.parseCourse(line);
if (result.isSuccess()) {
    drafts.add(result.draft());
} else {
    errors.add(new RowError(rowNumber, result.error(), result.message()));
}
```

`ParseError` — enum, а не строка: опечатку ловит компилятор, а `switch` по нему
обязан быть полным. Сообщение (`message`) — для человека, `error` — для кода.
Тесты будут проверять `error`, а не текст (см. задание 12: проверка точного
текста — хрупкий тест).

**Что не сохраняется и почему.** Внутри ловится `NumberFormatException`, но его
`cause` **не** кладётся в результат:

```java
} catch (NumberFormatException ex) {
    return ParseResult.failure(ParseError.INVALID_HOURS, "часы '" + rawHours + "' не число");
}
```

Причина: `NumberFormatException` — внутренняя деталь реализации `Integer.parseInt`.
Сохранив её, мы (а) создадим зависимость тестов от формата сообщения JDK
(оно меняется между версиями), (б) потащим в результат бесполезный
`For input string: "abc"`. Причина отказа уже выражена `ParseError.INVALID_HOURS` —
это и есть нужная информация. Аналогично с `CourseImportException` в задании 6:
там `cause` сохраняется, потому что там мы **не смогли** выразить причину
достаточно (запись файла, номер строки, физическая причина сбоя).

## 3. `enroll` → типизированный результат

```java
public EnrollmentResult enroll(long studentId, CourseCode courseCode) {
    if (studentId <= 0) {
        throw new IllegalArgumentException("studentId должен быть положительным");
    }
    return switch (courseCode.value()) {
        case "JAVA-101" -> EnrollmentResult.accepted(studentId, courseCode);
        case "JAVA-102" -> EnrollmentResult.rejected(studentId, courseCode, ErrorCode.COURSE_CLOSED);
        case "JAVA-103" -> EnrollmentResult.waitlisted(studentId, courseCode);
        default         -> EnrollmentResult.rejected(studentId, courseCode, ErrorCode.COURSE_NOT_FOUND);
    };
}
```

Здесь видно главное различие, ради которого задание и существует. В одном методе
живут **оба** вида ошибок, и они принципиально разные:

* `studentId <= 0` → `IllegalArgumentException`, **unchecked**. Программист
  передал значение, которого быть не может. Компилятор не может это проверить,
  но и «поймать» нечего: чинить надо вызывающий код;
* «курс закрыт» → `EnrollmentResult.rejected(...)`, **значение**. Это
  бизнес-правило, оно работает, система функционирует правильно. Пользователь
  получит «курс закрыт», и это нормальный ответ.

Если сделать отказ зачисления исключением, то самые частые исходы (курс закрыт,
нет пререквизита, дубликат) окажутся в `exceptional path`, а вызывающий будет
обязан писать `try/catch` вокруг каждого зачисления. Хуже: `try/catch` вокруг
метода легко забыть, и тогда отказ просто не обработается.

**Защита границы ожидаемого результата.** `EnrollmentService.enroll` всегда
возвращает `EnrollmentResult`. Но бывают команды, где отказ недопустим и должен
быть виден как ошибка. Для них — `enrollOrFail`, который превращает **ожидаемый
доменный отказ** в исключение:

```java
public EnrollmentResult enrollOrFail(long studentId, CourseCode courseCode) {
    EnrollmentResult result = enroll(studentId, courseCode);
    return switch (result.status()) {
        case ACCEPTED, WAITLISTED -> result;
        case REJECTED -> throw new EnrollmentRejectedException(
                studentId, courseIdOf(courseCode), reasonOf(result.reason()));
    };
}
```

Граница проходит по названию метода: `enroll` — «может отказать, верни значение»,
`enrollOrFail` — «обязан succeed, иначе это ошибка вызывающего кода». Решение
принимает тот, кто вызывает, у которого есть контекст.

## 3a. `enroll` в двух слоях

В `CourseService.enroll` отказ — это значение:

```java
public EnrollmentResult enroll(long studentId, CourseCode courseCode) { ... }
```

Но в проекте есть и второй метод с тем же именем — `EnrollmentService.enroll`
(задание 13). Разница в требовании вызывающего:

| Метод | Что возвращает | Когда нужен |
|---|---|---|
| `CourseService.enroll` | `EnrollmentResult`, отказ — это значение | Обычный сценарий: отказ ожидаем |
| `EnrollmentService.enroll` | то же самое | Ядро сценария, отказ уходит вверх |
| `EnrollmentService.enrollOrFail` | то же, но отказ → `EnrollmentRejectedException` | Вызывающий обязан получить успех или исключение |

`enrollOrFail` — пример того, как один и тот же доменный код обслуживает
две разные потребности: «разбери исход» и «у меня должен быть успех».

## 4. `calculatePrice` → checked-исключение

```java
public long calculatePrice(long studentId, int hours) throws PaymentGatewayException {
    if (hours <= 0) {
        throw new IllegalArgumentException("количество часов должно быть положительным");
    }
    if (studentId == 7777L) {
        throw new PaymentGatewayException("платёжный шлюз недоступен, student=" + studentId);
    }
    return hours * 500L;
}
```

Платёжный шлюз лежит — это **внешнее** условие, оно пройдёт само (или нет).
У вызывающего есть осмысленные варианты: повторить с backoff, поставить в
очередь, показать «попробуйте позже». `throws` заставляет написать один из них
явно, а не спрятать.

Смотрите на вывод `Demo7`:

```
цена: 20000
шлюз упал: платёжный шлюз недоступен, student=7777
unchecked пролетел мимо catch: количество часов должно быть положительным
```

Последняя строка — ключевая. `catch (PaymentGatewayException ex)` **не** поймал
`IllegalArgumentException`, потому что это разные вещи: ошибка вызывающего
против отказа внешнего мира. Если бы мы написали `catch (Exception)`, ошибка
вызывающего спряталась бы среди «внешних» и мы бы сообщили пользователю
«шлюз недоступен» из-за того, что передали `-5`.

## Сводная таблица

| Ситуация | Форма | Формальность |
|---|---|---|
| «Не нашлось» | `Optional.empty()` | значение |
| «Несколько причин отказа» | типизированный result | значение |
| «Бизнес-правило не выполнено» | типизированный result | значение |
| «Внешний сервис недоступен» | checked-исключение | control flow |
| «Ты передал ерунду» | unchecked-исключение | баг |
| «Нет такой операции в этом состоянии» | unchecked `IllegalStateException` | баг порядка вызовов |

## Почему результат — `record`, а не класс

```java
public record EnrollmentResult(Status status, long studentId,
                               CourseCode courseCode, ErrorCode code) { ... }
```

У результата-зачения три свойства, которые вручную писать не хочется:

* `equals`/`hashCode` по всем полям — иначе `assertEquals(expected, actual)`
  в параметризованных тестах упадёт непонятно или, что хуже, пройдёт;
* неизменяемость — отказ нельзя «случайно» починить, получив ссылку;
* `toString` — для сообщений об ошибке и вывода в демо.

`record` даёт всё это сам, поэтому здесь он и выбран. Тот же довод
работает для `ParseResult` и `OperationResult` в задании 15.

## Общее правило выбора

Задайте себе один вопрос: **что вызывающий сделает с этим отказом?**

* ничего, это нормальный исход → значение (`Optional`, result);
* повторить/показать пользователю/прервать операцию → checked-исключение;
* исправить код → unchecked-исключение;
* ничего не поможет, нужен корректный выход → `Error`, не ловим (задание 2, №6).
