# Задание 3. Собственное исключение

Код: `EnrollmentRejectedException.java` (сам класс) и `Demo3.java` (демонстрация).

```bash
./mvnw -q compile
java -cp target/classes level1.Demo3
```

## Что было не так в исходном варианте

Файл назывался `Demo3.java`, а публичный класс внутри — `EnrollmentRejectedException`.
В Java **имя публичного класса обязано совпадать с именем файла**, иначе компилятор
даёт ошибку `class EnrollmentRejectedException is public, should be declared in a file
named EnrollmentRejectedException.java`. Класс вынесен в отдельный файл, а `Demo3`
теперь его использует.

## Три требования и как они выполнены

### 1. studentId, courseId, reason code

```java
private final long studentId;
private final long courseId;
private final Reason reason;      // enum, а не String
```

`Reason` — это enum из четырёх значений (`NO_SEATS`, `PREREQ_MISSING`, `COURSE_CLOSED`,
`DUPLICATE`), а не строка. Причины:

* опечатку в значении находит компилятор, а не продакшен;
* `switch` по enum обязателен обработать полностью — забыть ветку нельзя
  (в `Demo3.userMessage` компилятор требует все четыре);
* при выводе наружу можно отдать не текст, а сам `reason`, и пусть вызывающий
  решает, как это показать.

Поля `private final` + геттеры вместо публичных полей: значение нельзя случайно
подменить после создания исключения (иначе причина ошибки перестала бы соответствовать
сообщению).

### 2. Сохранение исходной причины

```java
public EnrollmentRejectedException(long studentId, long courseId, Reason reason, Throwable cause) {
    super("Enrollment rejected [reason=" + reason + "]", cause);
    ...
}
```

`cause` передаётся в `super(...)`. Это главное, что обычно теряют при оборачивании.

Цепочка `getCause()` читается в цикле и даёт полную картину:

```
[0] ru.coursehub.EnrollmentRejectedException: Enrollment rejected [reason=PREREQ_MISSING]
[1] java.io.IOException: connect timed out after 30000 ms
```

**Почему нельзя "просто поймать и не бросить"** — типичная ошибка:

```java
try {
    checkPrerequisites(student);
} catch (IOException e) {
    throw new EnrollmentRejectedException(studentId, courseId, Reason.PREREQ_MISSING); // причина потеряна
}
```

В логе будет «заявка отклонена, нет пререквизита», а инженер не найдёт, что сеть
отвалилась 30 секунд назад. Причина уехала в никуда, диагностика превратилась в гадание.
Второй вариант — ещё хуже:

```java
catch (IOException e) {
    e.printStackTrace();                       // напечатали и забыли
    throw new EnrollmentRejectedException(...); // ...и всё равно потеряли связь
}
```

Печать в поток ошибок не является сохранением причины. Причина хранится в объекте.

### 3. Сообщение и toString не раскрывают лишние данные

```java
super("Enrollment rejected [reason=" + reason + "]", cause);   // без id

@Override
public String toString() {
    return "EnrollmentRejectedException[reason=" + reason
            + ", hasCause=" + (getCause() != null) + "]";     // без id
}
```

Что здесь важно и почему:

* **id студента и курса не попадают в текст.** Сообщение исключения часто уезжает
  в логи, в ответы API, в агрегаторы, в письма поддержке. Персональный идентификатор
  в этих текстах — лишнее раскрытие данных;
* **но данные не выбрасываются.** `studentId()` и `courseId()` остаются доступны
  программно — вызывающий, которому они нужны для логирования или ответа, их получит.
  «Не раскрывать» ≠ «не хранить»;
* **вместо id выводится `hasCause`.** Разработчик сразу видит: «это обёртка, искать
  надо глубже», — и кликает по стектрейсу, не читая текст;
* **нет пути к файлу, порту, URL, SQL.** Такие детали в тексте — источник утечек
  (внутренние хосты, структура БД) и источник хрупких тестов: в задании 12 отдельный
  пункт как раз про тесты, проверяющие точный текст `toString`.

## checked или unchecked?

`extends RuntimeException` — **unchecked**. Обоснование:

* отказ в зачислении — ожидаемый бизнес-исход, а не сбой окружения;
* если бы класс был checked, каждая цепочка `enroll -> ... ->` тащила бы `throws`,
  хотя вызывающий всё равно обязан разобрать исход заявки — иначе он не сможет
  ответить пользователю, что произошло;
* внутри доменного слоя исключение удобно: успешный путь остаётся чистым.

Но на **публичной границе** (уровень V, задание 15) это исключение не доходит
до клиента как есть: наружу отдаётся `ErrorCode`. Иначе клиент (UI, REST) завязался бы
на Java-типы и на их имена, а любое переименование класса стало бы ломающим изменением.
