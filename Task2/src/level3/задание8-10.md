## Задание 8. Первый тест по AAA

`test/level3/CourseCompletionTest.java`

AAA = **A**rrange / **A**ct / **A**ssert. Не «надо разделить на три блока для
красоты», а способ удерживать в тесте одну причину падения.

```java
// Arrange
Course course = Course.of("JAVA-101", "Основы Java", 30);

// Act
course.completeHours(24);

// Assert
assertEquals(24, course.completedHours(), "...");
```

Три правила, которые за этим стоят:

1. **В Arrange нет действий над объектом под тестом.** Только создание и
   настройка. Если в Arrange что-то «подготовить» вызовом `completeHours`, то
   падение в этом вызове будет выглядеть как падение теста, а на самом деле
   это будет падение фикстуры;
2. **В Act — ровно одно действие.** Два вызова подряд — это уже два акта,
   и непонятно, какой из них причина падения. Если нужно два действия,
   это два теста;
3. **В Assert — только проверки.** Никаких вызовов над SUT.

### Одна причина падения

`completeHours` проверяется **двумя** тестами, а не одним:

```java
@Test void completeHoursStoresGivenValue()   // проверяет значение
@Test void completeHoursMarksCourseAsCompleted()  // проверяет флаг
```

Если бы было одним:

```java
@Test
void completeHours() {
    Course course = Course.of("JAVA-101", "Основы Java", 30);
    course.completeHours(24);
    assertEquals(24, course.completedHours());
    assertTrue(course.isCompleted());
}
```

то при падении непонятно, что сломалось: сохранение значения или вычисление
флага. Пришлось бы ставить breakpoints и гадать. Два теста дают два разных
сообщения об ошибке — диагностика в подписи метода.

### Имя теста — документация

```java
@DisplayName("успешный вызов сохраняет переданное количество часов")
void completeHoursStoresGivenValue() {
```

`@DisplayName` показывается в отчёте и в IDE. Имя отвечает на вопрос
«что проверяется», а не «какой метод вызывается»: `completeHours` и так видно
в стектрейсе, а вот «успешный вызов» / «отказ во вне границ» — нет.

Сообщение в `assertEquals` — последняя линия диагностики, его видно, когда
тест падает в CI без IDE.

## Задание 9. Граничные значения

`test/level3/CourseDurationBoundariesTest.java`

Покрыты: ниже минимума (0, 9), минимум (10), максимум (40), выше максимума
(41, 100), плюс «на единицу за границей» (9 и 41).

### Почему «обычный» пример не фиксирует контракт

```java
@Test
void completeHours() {
    Course course = Course.of("JAVA-101", "Основы Java", 30);
    course.completeHours(20);          // «обычное» значение
    assertEquals(20, course.completedHours());
}
```

Тест зелёный. Что он на самом деле утверждает? **Ровно одно**: «20 допустимо».
Он не утверждает ничего про 9, 41, 0, -5. При этом контракт метода —
это диапазон `[10..40]`, а не единственное число 20.

Конкретные способы, как такой тест обманывает:

* **Ошибка «<» вместо «<=».** Реализацию меняют на
  `if (hours <= MIN_DURATION_HOURS) throw ...` — 10 теперь отвергается.
  Тест с 20 по-прежнему зелёный. Баг доживает до продакшена, и падает он на
  данных, где ровно 10 часов (а таких курсов полно);
* **Ошибка в константе.** `MAX_DURATION_HOURS` поменяли с 40 на 50.
  «Обычный» тест не заметит. Тест на границах, ссылающийся на
  `Course.MAX_DURATION_HOURS`, переживёт изменение контракта;
* **Отсутствие нижней границы.** Убрали проверку минимума целиком — тест
  с 20 снова зелёный, а `completeHours(1)` теперь принимает ерунду;
* **Тест на «не бросило».** Частая замена:
  `assertDoesNotThrow(() -> course.completeHours(20))` — он прошёл бы и при
  0, и при 999. Такой тест вообще ничего не проверяет.

Общее правило: **тест должен утверждать контракт, а не пример**. Для
диапазона это значения на границах плюс значения сразу за ними.

### Про `-5`

В таблице `rejectsValuesOutOfRange` есть `-5` с ожиданием «меньше минимума».
Отдельного сообщения «отрицательные часы недопустимы» нет намеренно: `-5 < 10`,
и это тот же контракт «вне диапазона». Дублировать ветку ради красивого текста
не нужно — иначе правило «часы вне [10..40]» придётся поддерживать в двух местах.

### Про текст сообщений

```java
@CsvSource({
        "0,  меньше минимума",
        "41, больше максимума"
})
void rejectsValuesOutOfRange(int hours, String expectedHint) {
    IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
            () -> course.completeHours(hours));
    assertTrue(ex.getMessage().contains(expectedHint), "...");
}
```

Проверяется **смысл** сообщения (есть ли в нём объяснение проблемы), а не
точная строка. Точный текст — деталь реализации: его переводят на другой язык
или уточняют, и тест падает, хотя поведение не изменилось. Это прямой заход
в задание 12.

## Задание 10. Параметризованный тест

`test/level3/CourseCodeTest.java`

### `@CsvSource` — данные рядом с тестом

```java
@ParameterizedTest(name = "вход ''{0}'' -> ожидаем ''{1}''")
@CsvSource({
        "JAVA-101,      JAVA-101",
        "java-101,      JAVA-101",
        "  java-101  ,  JAVA-101",
        "java_101,      JAVA-101",
        "'java 101',    JAVA-101"
})
void normalizesInput(String raw, String expected) { ... }
```

Это 8 отдельных тестов с одним кодом. Без параметризации пришлось бы написать
8 почти одинаковых методов, и при добавлении ещё одного варианта — ещё один
метод.

**`name = "вход ''{0}'' -> ожидаем ''{1}''"`** — плейсхолдеры подставляются
в имя теста. При падении в отчёте сразу видно:

```
[2] вход 'java_101' -> ожидаем 'JAVA-101'
```

и не нужно открывать код, чтобы понять, какой вход не сработал. Это ровно
требование задания: «Display name должен показывать вход и ожидаемый результат».

Двойные кавычки `''` внутри строки — экранирование, потому что одинарные
кавычки в `@CsvSource` означают «строка с запятой внутри» (`'java 101', JAVA-101`
одним значением).

### `@ValueSource` — одно значение на строку

```java
@ParameterizedTest(name = "недопустимый код ''{0}'' -> отвергнут")
@ValueSource(strings = {"", "   ", "J", "JAVASCRIPT-101", "JAVA101", ...})
void rejectsInvalidCodes(String raw) { ... }
```

### `@MethodSource` — когда данные из кода

```java
@ParameterizedTest
@MethodSource("validityCases")
void isValidAgreesWithFactory(String raw, boolean expected) { ... }

static Stream<Arguments> validityCases() {
    return Stream.of(
            Arguments.of("AB-101", true),      // 2 буквы - минимум
            Arguments.of("ABCD-101", true),    // 4 буквы - максимум
            Arguments.of("A-101", false),      // 1 буква - мало
            Arguments.of("ABCDE-101", false)   // 5 букв - много
    );
}
```

Когда `@CsvSource` недостаточен:

* **нужно два и более параметров** — у `@ValueSource` только один;
* **данные зависят от кода** — например, диапазон констант. Тогда тест не
  «отстаёт» от изменений;
* **сложная подготовка** (объекты, списки, `null` в середине).

Метод-источник должен быть `static` (иначе JUnit не найдёт) и возвращать
`Stream<Arguments>`, `Stream<Collection<?>>`, `Stream<?>[]` или
`Iterable<Arguments>`. Метод не обязан быть публичным.

### Границы как отдельный тест

```java
@Test
void prefixLengthIsBounded() {
    for (int letters = 1; letters <= 6; letters++) {
        String code = "A".repeat(letters) + "-101";
        boolean shouldBeValid = letters >= 2 && letters <= 4;
        assertEquals(shouldBeValid, CourseCode.isValid(code), ...);
    }
}
```

Отдельный тест, который **фиксирует само правило** «от 2 до 4 букв», а не
набор случайных примеров. `@CsvSource` перечисляет кейсы; если правило
поменяют, примеры останутся старыми и ничего не поймают.

### Чего в тестах нет намеренно

* `assertEquals("CourseCode[value=JAVA-101]", code.toString())` — проверка
  точного текста `toString` ломается при любом изменении форматирования.
  Проверяют поля, а не их склейку (см. задание 12);
* `assertNotNull(code)` после успешного `of()` — бессмысленно: если бы
  `of()` вернул null, следующая проверка `code.value()` упала бы с NPE.
  `assertNotNull` имеет смысл только там, где null допустим;
* сравнения `assertEquals(course1, course2)` для объектов без `equals` —
  сравнилась бы ссылка, а не состояние. У `CourseCode` `equals` есть и
  проверяется явно.
